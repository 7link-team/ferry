# 应用市场与集群模板设计

状态：设计稿，待用户审阅；未实现。清单编号 MARKET-SOURCES-65。
上位文档：`docs/prd/应用高可用拓扑与多部署驱动方案.md`（§1 分层、§3 寻址矩阵、§11 场景模板与市场来源）。本文是其中「市场来源 + 集群模板」的可实施设计，不替换该文档的实验与验收结论。

## 1. 意图

用户原话归纳：

- 应用市场要像 `helm repo add` 一样在**平台设置**里添加多个来源，由官方或开源社区维护，**所有客户工作空间开箱可见、可导入**。
- 每个工作空间仍可添加**自己的**来源（公有或私有）。
- 模板内容以 Git 仓库管理。
- 模板必须支持**集群/HA**，且**不能写死 IP**：纯 Native 场景多用 IP/主机名，Docker/Compose/Swarm（以及将来的 K8s）使用服务发现。要**全场景覆盖**。
- 首批 HA 模板全部要做：PXC、Redis Sentinel、NATS、Nginx、XXL-JOB、Ferry 自身。
- K8s 驱动本期不做，但**必须保证以后的可扩展性**。
- 参考：1Panel 太单机，Helm 太 K8s/太重，Nomad（Nomad Pack + 作业模型）值得参考。

为什么：现在的市场只有空间级来源、单个 JSON 内嵌全部内容、只能导入单一应用模板（连 Redis Sentinel 示例依赖的配置文件模板都带不过去），HA 只能靠参数填 `ip_a/ip_b/ip_c` 再复制服务，既不能跨驱动复用，也无法由官方统一分发。

## 2. 目标 / 非目标 / 反目标

**目标**

1. 平台级市场来源：超级管理员在平台设置中增删改、同步；仅公开仓库；全部工作空间可见可导入。
2. 空间级市场来源：保持现有能力（公有/私有、凭据、定时任务同步），兼容现有 v1 索引。
3. 新的模板仓库协议（索引 v2）：每应用一个目录、多版本、附带配置文件模板、README、图标、元数据；CI 生成单一 bundle 供同步。
4. 集群蓝图（Blueprint）：模板声明「角色 + 实例数 + 放置约束 + 成员引用」，部署时绑定主机，由驱动适配器编译为现有 `ferry/v2 Application` 执行产物。
5. 寻址按驱动抽象：Native/跨机 Docker 用主机地址；Compose 用服务名；Swarm 用每实例独立 service 的稳定 DNS 名；K8s 预留 StatefulSet + headless DNS 语义。
6. 六个 HA 模板按「模板 × 驱动」逐项实测验收后标记「已验证」。

**非目标（本期不做）**

- K8s 驱动实现（只预留适配接口与寻址语义）。
- 平台级来源接私有仓库、平台级凭据保管。
- 全停恢复（全部成员同时宕机后的自动选主/bootstrap 恢复）与自动故障替换（节点失联后系统自动迁移）。扩缩容和手动换主机**在范围内**，见 §7.1。
- 模板上游更新后自动更新已导入副本；版本差异对比页面。
- 流水线、节点工作流、仓库连接类模板进市场（§11 另行推进，协议预留 `kind`）。
- 跨应用依赖图（如 Ferry 模板自动依赖 PXC/NATS 应用）：本期以参数填写外部端点。

**反目标（即使能跑也算失败）**

- 模板里出现写死的 IP、容器临时 IP、`localhost` 回退作为成员地址。
- 驱动不支持某蓝图时静默生成「看似可用」的配置；必须编译期拒绝并给出原因。
- 未实测的「模板 × 驱动」组合显示为「已验证」。
- 同步失败破坏上一次可用目录；上游变更改动用户已导入的模板或已部署应用。
- 平台来源让某工作空间看到/影响其他工作空间的数据。

## 3. 参考与取舍

| 来源 | 借鉴 | 不采用 |
|---|---|---|
| Nomad Pack | 模板库即 Git 仓库；`packs/<name>/` 目录含元数据、变量、模板、README；registry add 后直接用 | HCL 语法、consul-template 渲染 |
| Nomad 作业模型 | task group（角色）+ count + `distinct_hosts`/spread 约束 + 实例序号 `NOMAD_ALLOC_INDEX` | 依赖 Nomad 调度器 |
| Helm | `repo add`、索引带版本与校验和、values 覆盖默认值 | K8s 资源模型、tgz 打包 |
| 1Panel | 每应用一个目录，图标/说明/多版本子目录 | 单机 compose 即应用 |

外部样本只用于结构表达；字段、状态、权限、接口以本项目代码为依据（见 §11 事实来源）。Nomad Pack 细节凭已有知识，实施前核对官方文档。

## 4. 总体架构

```
Git 仓库（源目录）──CI生成──> index.json(bundle v2)
        │  平台来源（公开，平台worker定时/手动同步）
        │  空间来源（公有/私有，空间定时任务/手动同步）
        ▼
marketplace_entries（每 来源×包×版本 一行，全部校验通过才整批替换）
        │  导入（选版本）
        ▼
本空间 app_templates（+ 附带 config_templates），记录来源/包/版本
        │  创建应用：填参数 + 角色实例绑定主机 + 选驱动
        ▼
Blueprint 编译器（驱动适配器：native / docker / compose / stack / [k8s 预留]）
        │  输出：每目标一份 ferry/v2 Application
        ▼
现有部署执行（deployments + revision targets + 每目标状态）
```

关键约束：编译产物仍是现有 `ferry/v2 Application`，执行、状态、回滚、审计全部复用；新增的只是「蓝图层」和「编译层」。这与上位文档 §1「同一个应用蓝图按驱动生成目标计划，复用 ferry/v2 Application 作为每目标执行产物」一致。

## 5. 仓库协议（索引 v2）

### 5.1 源目录（人维护）

```
<repo>/
  ferry-repo.json                 # 仓库元数据：schemaVersion、名称、维护者、主页
  apps/<key>/
    package.json                  # 包元数据（见5.3），与版本无关的部分
    icon.svg | icon.png           # 可选，≤64KiB
    <semver>/
      blueprint.json              # kind=Blueprint 或 Application
      parameters.json             # 参数定义（沿用现有 Parameter 结构）
      files/<name>                # 配置文件模板（沿用 config_templates 语法）
      README.md                   # ≤64KiB
      verified.json               # 可选：已验证的 驱动×版本 及证据链接
  scripts/build-index             # CI：校验 + 生成 index.json
  index.json                      # 生成物，提交到仓库
```

### 5.2 同步读取的 bundle（机器读）

同步时只请求 `index.json` 一个文件（GitHub 匿名 60 次/小时 足够；沿用现有 provider 文件 API 读取，不执行 git）。

```json
{
  "schemaVersion": 2,
  "generatedAt": "2026-11-11T00:00:00Z",
  "packages": [
    {
      "key": "redis-sentinel",
      "kind": "app",
      "meta": { "...": "package.json 内容" },
      "icon": "data:image/svg+xml;base64,...",
      "versions": [
        {
          "version": "1.0.0",
          "requires": { "ferry": ">=0.9.0" },
          "blueprint": { "...": "..." },
          "parameters": [],
          "files": [{ "name": "redis-start.sh", "content": "...", "parameters": [] }],
          "readme": "...",
          "verified": [{ "driver": "compose", "ferry": "0.9.0", "evidence": "https://..." }],
          "sha256": "<blueprint+parameters+files 规范化后的摘要>"
        }
      ]
    }
  ]
}
```

- `schemaVersion=1`（现有 `{version:1,templates:[...]}`）继续按旧逻辑解析，导入结果等同 v2 中 `kind=app`、单版本 `0.0.0`、无文件的包。
- 未知 `schemaVersion`、未知 `kind`、`requires.ferry` 不满足的版本：整个版本条目标记「不兼容」入库但不可导入（不让整批同步失败），在界面显示原因。其余结构错误按现有规则整批失败、保留旧目录。
- bundle 上限由 2MiB 提高到 8MiB；包 ≤500，每包版本 ≤20，每版本文件 ≤20、单文件 ≤256KiB。

### 5.3 package.json

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| name | `{locale: string}` | 是 | 至少 zh-CN 或 en-US；每项 1–60 字符 |
| description | `{locale: string}` | 否 | 每项 ≤500 字符 |
| category | string | 是 | 枚举：database / cache / messaging / web / scheduler / platform / other |
| topology | string | 是 | `single` / `cluster` |
| drivers | string[] | 是 | 子集：native / docker / compose / stack / k8s（k8s 本期只能出现在声明里，编译器拒绝） |
| tags | string[] | 否 | ≤10 项，每项 ≤30 |
| maintainers | string[] | 否 | ≤10 |
| homepage | string | 否 | https URL |

多语言名称按请求语言回退：请求语言 → en-US → zh-CN → key。

## 6. 集群蓝图（Blueprint）

### 6.1 形态

`apiVersion: ferry/blueprint-v1`, `kind: Blueprint`。`kind: Application`（现有 v2）仍可作为单机模板。

```json
{
  "apiVersion": "ferry/blueprint-v1",
  "kind": "Blueprint",
  "metadata": { "name": "redis-sentinel" },
  "roles": [
    {
      "name": "redis",
      "instances": { "min": 3, "max": 9, "default": 3, "odd": false },
      "placement": { "distinctHosts": true },
      "identity": "stable",
      "ports": [{ "name": "data", "container": 6379, "published": "{{ .Values.data_port }}" }],
      "service": { "...": "ferry/v2 Service 字段，可用 .Instance / .Role 引用" }
    },
    {
      "name": "sentinel",
      "instances": { "min": 3, "max": 7, "default": 3, "odd": true },
      "placement": { "distinctHosts": true, "colocateWith": "redis" },
      "identity": "stable",
      "ports": [{ "name": "sentinel", "container": 26379, "published": "{{ .Values.sentinel_port }}" }],
      "service": { "...": "..." }
    }
  ],
  "endpoints": [
    { "name": "client", "role": "sentinel", "port": "sentinel", "kind": "discovery" }
  ],
  "drivers": {
    "stack": { "supported": true, "memberAddressing": "per-instance-service" },
    "native": { "supported": true }
  },
  "update": { "maxParallel": 1, "minHealthySeconds": 10, "healthTimeout": 180, "autoRevert": true },
  "hooks": [
    { "event": "post-add",    "role": "sentinel", "run": "existing", "command": ["redis-cli", "-p", "{{ .Instance.Port \"sentinel\" }}", "SENTINEL", "RESET", "*"] },
    { "event": "pre-remove",  "role": "redis",    "run": "target",   "command": ["sh", "/etc/example-redis-start.sh", "leave"] }
  ],
  "strategy": { "type": "recreate", "healthTimeout": 180 }
}
```

- `identity: stable`：每实例有稳定名 `<role>-<index>`、独立卷、独立通告地址；`stateless`：允许用一个服务 + replicas（如 Nginx）。
- `placement.distinctHosts`：同角色实例不得落在同一主机；`colocateWith`：与另一角色同序号实例同主机（Sentinel-i 跟 Redis-i）。
- `update`（参考 Nomad `update` 块）：滚动更新时每批最多变更几个实例、实例健康后需稳定多久、单批健康超时、失败是否自动回滚到上一修订。有状态角色的 `maxParallel` 校验时强制为 1。
- `hooks`（参考 Helm hooks）：事件 `pre-add / post-add / pre-remove / post-remove / pre-upgrade / post-upgrade`；`run: target` 在被增删的实例里执行，`existing` 在每个保留的同角色实例里依次执行，`any` 在任一健康的保留实例里执行一次。命令可用 `.Instance` 和 `.Role`（变更后的成员视图）。钩子非零退出码或超时（默认 120 秒，上限 600 秒）视为该批失败。
- **模板没有声明某类变更所需的钩子，该变更就被拒绝**（模板通过 `roles[].scaling: none | add-only | add-remove` 声明能力，默认 `none`）。没有钩子的有状态服务只能升级参数和版本，不能改拓扑，避免集群被搞坏。

### 6.2 模板变量（在 `.Values` 之外新增）

| 变量 | 含义 |
|---|---|
| `.Instance.Role` / `.Instance.Index` / `.Instance.Name` | 当前实例角色、从 0 开始的序号、稳定名 `redis-0` |
| `.Instance.Host` | 当前实例的**通告地址**（由驱动解析，见 6.3） |
| `.Instance.Port "<portName>"` | 当前实例该端口的**对外可达端口** |
| `.Role "<name>"` | 该角色全部实例列表，元素含 `.Name .Index .Host` 与 `.Port "<portName>"` |
| `.Deployment.Driver` | 当前驱动，供少数必须分支的模板使用 |

现有渲染器（`templates.rs`）只做 `{{ .Values.x }}` 占位替换，不支持循环、条件和带参数的函数调用。本期**实现一个受限的 Go-template 子集**（我的判断）：
- 支持 `{{ range .Role "<name>" }}…{{ end }}`、`{{ if }}/{{ else }}/{{ end }}`、`.Port "<name>"`、`join`、`default`、现有 `ceilMinutes`。
- 不支持自定义函数、模板嵌套和任意表达式；循环次数上限等于实例数（≤100）。
- secret 参数仍只能出现在现有允许的 `valueFrom` 字段路径上，**不能出现在 range/if 块内**，校验时拒绝。

示例（NATS 路由）：
`{{ range .Role "nats" }}nats://{{ .Host }}:{{ .Port "cluster" }} {{ end }}`

### 6.3 驱动寻址（编译器解析 `.Host`/`.Port`）

| 驱动 | 实例落地 | `.Host` | `.Port` | 本期 |
|---|---|---|---|---|
| native | 每实例一个目标主机，生成该主机的 v2 产物 | 绑定的通告地址（建议值取主机记录 `address`；若是回环地址、Runner 自报地址或经跳板机的地址，必须由用户逐个确认或改为成员可达的私网 IP/主机名，未确认不能提交） | published 端口 | 实现 |
| docker（跨机独立） | 同 native，容器发布端口 | 同上 | published | 实现 |
| compose（单机） | 所有实例为同一 compose 项目内的服务 `<role>-<i>` | 服务名 `redis-0` | container 端口 | 实现；`distinctHosts` 在单机无法满足 → 仅当模板声明 `allowSingleHost: true` 时允许（演示/开发），界面标「非 HA」 |
| stack（Swarm） | `identity:stable` 每实例一个 service `<role>-<i>`，`placement` 固定 `node.hostname==<绑定节点>`，端口用 host 模式发布，manifest 新增 `endpointMode: dnsrr`；`stateless` 一个 service + replicas + VIP | stable：绑定节点的通告地址（同 native 确认规则），不使用 VIP；stateless：VIP 服务名 | stable：host 模式发布端口；stateless：container 端口 | 实现 |
| k8s | stable → StatefulSet + headless Service；stateless → Deployment + Service | `<role>-<i>.<role>.<ns>.svc` | container 端口 | **预留**，编译器返回「驱动未实现」 |

- 客户端需要从集群外访问的端点（`endpoints` 中 `kind: discovery|vip|direct`）单独渲染，不与成员地址混用（上位文档 §3 四类地址分开）。
- 模板在 `drivers.<d>.supported=false` 或缺省时，该驱动不可选；编译期检查失败给出具体原因（如「Redis Sentinel 需要可通告地址，Swarm VIP 不满足」）。

### 6.4 编译器扩展点（可扩展性要求）

后端新增 `blueprint` 模块：

```rust
trait DriverAdapter {
    fn id(&self) -> &'static str;                       // "native" | "docker" | "compose" | "stack" | "k8s"
    fn check(&self, bp: &Blueprint, binding: &Binding) -> Result<()>;   // 约束、端口冲突、寻址可行性
    fn resolve(&self, bp: &Blueprint, binding: &Binding) -> Result<Topology>; // 每实例 Host/Port
    fn compile(&self, bp: &Blueprint, topo: &Topology, values: &Values) -> Result<Vec<TargetPlan>>; // 每目标 ferry/v2
}
```

- 新增 K8s 只需新增一个 adapter + 部署执行驱动，不改蓝图协议、不改市场协议。
- 生命周期钩子（bootstrap/scale/replace）以后以 `trait LifecycleAdapter` 按服务扩展。

## 7. 部署时绑定（Binding）

创建应用（选择 Blueprint 模板）时：

1. 选驱动（只列模板声明支持的）。
2. 每角色设实例数（在 min/max/odd 内，默认 default）。
3. 绑定：
   - native/docker：逐实例选主机；或选主机组「按顺序自动分配」后可逐个改。每实例可覆盖通告地址。
   - compose：选一台主机。
   - stack：选 Swarm manager 主机，逐实例选节点主机名（来自该 Swarm 的节点列表）。
4. 填 `.Values` 参数（现有参数表单）。
5. 预览：显示每实例的名称、主机、通告地址、端口、编译产物摘要；约束不满足禁止提交。

绑定存入部署记录（新增 `blueprint_binding` 字段，见 §9），每次修订快照保存；编译产物写入现有 revision targets，执行路径不变。

### 7.1 修改拓扑（扩缩容、换主机）

用户确认：部署后允许修改实例数和实例所在主机，但必须平滑。参考 Nomad 的 `job plan` + `update` 和 Helm 的 `upgrade/rollback` + hooks：

1. **先计划再执行**（参考 `nomad job plan` / `helm diff`）：编辑绑定后点「预览变更」，系统给出逐实例的变更计划，按类型分为：新增、删除、原地更新（参数/镜像变化）、迁移（换主机 = 新增 + 删除）、不变。每项显示所在主机、数据影响（「数据卷不随迁移搬运，新实例从集群同步」等由模板声明的说明）、将执行的钩子。计划不可执行的原因逐条列出（实例数越界、偶数仲裁、违反 distinctHosts、模板不支持该变更、主机不可达）。
2. **确认后生成新修订**：修订号递增，快照保存蓝图 + 新绑定 + 参数 + 计划；可在历史里查看每次计划与结果。
3. **按批滚动执行**（参考 Nomad `update`）：
   - 顺序：先新增，再原地更新，最后删除；迁移拆成「新增新实例 → 健康 → 删除旧实例」，任何时候不先删后加。
   - 每批 ≤ `maxParallel` 个实例；每批：pre 钩子 → 部署/停止 → 健康检查 → 稳定 `minHealthySeconds` → post 钩子 → 下一批。
   - 缩容按 StatefulSet 语义删除**序号最大**的实例，保留其余实例的名称、序号和数据卷不变。
   - 成员视图：新增实例上线后，`.Role` 包含新成员并对保留实例重新渲染配置（按批原地更新）；删除实例在 pre-remove 之后才从成员视图中移除。
4. **失败处理**（参考 Helm `--atomic` / Nomad `auto_revert`）：任一批失败时停止后续批次；`autoRevert=true` 时按反方向回滚到上一修订的绑定（已新增的实例执行 pre-remove 后删除，已删除的实例无法自动恢复数据，计划阶段就提示）。`autoRevert=false` 时停在失败处，修订状态为「部分完成」，界面列出每个实例的实际状态，允许「重试本批」或「回滚到上一修订」。
5. **互斥**：同一应用同时只允许一个修订在执行（复用现有部署锁）；执行中禁止再次编辑拓扑。
6. **数据卷**：Ferry 不在主机之间复制数据卷。有状态服务换主机依赖服务自身复制（Redis 复制、PXC SST/IST、NATS JetStream 副本），模板必须在包元数据中声明 `dataMigration: replication | none`；`none` 的角色不允许迁移。删除实例后旧数据卷默认保留在原主机，界面提示可手动清理，不自动删除。

### 7.2 全平台兼容（用户要求：Windows / macOS / Linux）

> **2026-11-11 用户确认的分期**：现有 Native/Docker/Compose/Swarm 部署驱动都假定 POSIX shell、`flock`、`sha256sum`（Native 另需 systemd），`deployments/*` 不读 `hosts.os`，Windows/macOS 目标主机在预检阶段即失败。P2 只支持 Linux 目标主机；蓝图编译器按 `hosts.os` 判定，`os` 非空且不是 `linux` 的主机直接拒绝绑定并说明原因（SSH 主机 `os` 为空时按现状放行，由驱动预检兜底）。Windows 服务 / macOS launchd 的 Native 驱动与跨平台容器脚本单独立项，届时只新增驱动适配器，不改蓝图协议。下文规则作为该后续项目的目标保留。

目标主机可以是 Linux、macOS、Windows，Ferry 服务端与 Runner 本身已支持三平台（主机记录 `os`/`arch` 字段）。蓝图层规则：

- **编译器按目标主机 `os` 生成产物**：路径分隔符、工作目录、换行符、可执行文件后缀由驱动适配器处理，模板中只写逻辑路径（容器内路径始终是 Linux 路径）。
- **Native 驱动**：模板为每个 role 的 native 形态按 OS 声明 `native.<os>`（命令、配置文件路径、服务管理方式）；缺少某 OS 声明时该 OS 主机不可绑定，计划页说明原因。钩子同理：`hooks[].command` 可按 `os` 分别给出，容器内执行的钩子不区分 OS。
- **Docker 驱动在 Windows/macOS**：Docker Desktop / OrbStack / Colima 的容器跑在 Linux VM 中，host 网络模式与 Linux 不同。编译器对这些主机禁止 `network_mode: host`，统一使用端口发布；通告地址仍走 §6.3 的确认规则（不得用 VM 内地址）。Windows 容器（非 Linux 容器）本期不支持，检测到 Windows 容器模式直接拒绝。
- **Swarm**：仅 Linux 节点参与 stack 驱动的有状态实例绑定（Docker Desktop 的 Swarm 只能单节点，不构成 HA）；Windows/macOS 主机只允许作为 stateless 或单节点演示，计划页标「非 HA」。
- **测试矩阵**：P2 每个驱动至少在 Linux 真实多主机跑通；Windows、macOS 各至少一台真实主机验证 native 与 docker 单实例 + 一次升级回滚。不具备的平台组合在验收记录中标「未实测」，不显示「已验证」。

## 9. 数据模型（增量迁移，三库兼容）

现有表：`marketplace_sources`、`marketplace_entries`（迁移 `external_repository_marketplace_v1`）、`app_templates`、`config_templates`、`deployments`。

### 9.1 marketplace_sources（扩展）

平台来源以 `workspace_id = 0` 存储，与空间来源同表，所有现有空间查询已带 `workspace_id` 过滤，不会串入。

注意：现有同步/编辑/删除依赖工作空间事务（`variables::transaction` 锁工作空间）、`repositories.read` 权限和仓库/凭据绑定，平台来源都没有。所以**只复用表、索引解析与校验函数，平台来源的 CRUD 与同步是独立实现**：不加工作空间锁、不查仓库与凭据、请求不带 token、权限检查为超级管理员。

现有 `marketplace::recover` 在启动时把所有 `syncing` 改为 `failed`，多实例下会误伤其他实例正在进行的同步。平台来源改为租约字段：`sync_owner`（服务实例 ID 字符串）+ `sync_lease_until`，recover 只处理租约过期的行；空间来源的 recover 行为不变。

| 新增字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| trust | VARCHAR(16) NOT NULL | 'workspace' | workspace / official / community；平台来源只能 official/community |
| enabled | BIGINT NOT NULL | 1 | 平台来源停用开关 |
| sync_interval | BIGINT NOT NULL | 0 | 秒；0=不自动（空间来源沿用定时任务） |
| next_sync_at | BIGINT NOT NULL | 0 | 平台 worker 调度 |
| sync_owner | VARCHAR(128) NOT NULL | '' | 正在同步的服务实例 `AppState.instance_id`，空=无 |
| sync_lease_until | BIGINT NOT NULL | 0 | 租约到期时间 |
| created_by / updated_by / synced_by | BIGINT NOT NULL | 0 | 时间审计配对；0=system |

`repository_id` 对平台来源固定为 0。

### 9.4 deployments（扩展）

| 新增字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| blueprint_binding | TEXT NULL | NULL | 驱动、各角色实例数、每实例主机/节点/地址覆盖；NULL=非蓝图应用 |

蓝图应用与现有模型的关系（我的判断）：
- 新增 `target_kind = 'blueprint'`；`target_ref` 为 0，目标由 `blueprint_binding` 决定。现有 host / host-group 语义（组内每台主机部署同一产物）不变，也不拿来承载蓝图。
- `deployments.manifest` 存**蓝图快照**（导入模板的副本内容，不随模板之后的修改或删除变化，与现有「模板无活绑定」决策一致）。每次修订从该快照 + 绑定 + 参数重新编译。
- 编译时同一主机上的多个实例（同角色不可能，`colocateWith` 的可以）合并为该主机的一份 `ferry/v2 Application`，所以每台主机在一个修订中仍只出现一次，现有 error.054 约束保持成立。
- 每主机编译产物写入现有 `deployment_revision_targets`，执行、状态、回滚沿用现有路径。

DDL 的 up 均为 ADD COLUMN（带默认值），down 按项目惯例返回「不自动删除业务数据」。SQLite/PostgreSQL/MySQL 方言差异沿用现有 `long_text`/`create_table` 帮助函数。

## 15. 审阅后补充的判断（标注为设计方决定，可推翻）

1. **Swarm 节点绑定**：stack 驱动绑定的每个节点都必须已登记为本空间的 Ferry 主机；系统通过 manager 执行 `docker node ls` 按主机名匹配，未登记的节点不可选。这样「每个绑定主机逐一校验主机权限」在 stack 下同样成立。
2. **「已验证」标识**：只有 trust=official 的平台来源，其 `verified.json` 才显示为「已验证」；community 和空间来源显示为「作者声明」，避免未实测组合被标记为已验证。
3. **配置文件模板的上下文**：蓝图包附带的配置文件按**每个实例**渲染，自动获得包级 `.Values` 以及 `.Instance` 和 `.Role`，不需要在 `files[].values` 里逐项映射。导入时 `fromTemplate` 改写为导入后 config_template 的 ID。非蓝图应用的 `files[].values` 行为不变。
