# Ferry 与 LobeHub + n8n + ComfyUI：按完整任务对比

日期：2026-11-12。目的：判断哪些继续自研、哪些适合接入现成系统，以及 Ferry 是否有独立价值。**只研究，不更改产品范围、不实施集成、不部署服务。**

## 1. 结论先行

- 通用聊天、个人助手、常见业务集成和专业媒体生成：优先使用已有产品组合，Ferry 不应以追平这三个产品的总功能量作为成功条件。
- 仓库、主机、构建、部署和历史恢复：Ferry 已有可复核的领域实现，具备继续聚焦的基础；是否值得产品化仍取决于真实用户能否更省事地完成任务。
- “AI 在聊天中创建和执行工作流”已经不是独特卖点：当前 n8n 官方文档提供内置 MCP，支持搜索、调用、创建和编辑流程；从自然语言到流程本身不足以构成差异。
- 最值得保留的候选方向是运维/研发执行平台；最值得重新评估的是专业媒体引擎、海量集成连接器，以及为了追齐 LobeHub 而一次性开发整套记忆/自学习/多 Agent。
- 对自用，现成组合是强候选；对面向团队的产品，建议先验证 Ferry 的部署执行闭环，再决定投入。对需要商用分发或嵌入的产品，另行确认相应许可证，不能把“内部自托管”和“嵌入向客户提供”当成同一条件。

## 2. 本次验证方式与证据边界

完成：读取 Ferry 当前说明、部署/仓库/扩展文档与关键源码；获取并阅读11个 n8n/ComfyUI 官方文档页面；复用上一轮固定提交的 LobeHub 源码研究。Ferry 基础 HEAD 为 `57deabae953d3304c0cf5351b9168123e3a4a052`，工作区另有其他任务未提交的变更，本文引用的是当时工作区可见实现，不能冒称不可变发布快照。

未完成：没有搭起三产品联通环境，没有在两套方案实际执行部署/仓库/生成任务；没有测量搭建分钟数、运行延迟、故障恢复时间、GPU成本或用户满意度。以下“成本高低/适合度”是有证据的工程判断，不是测量结果。当前命令环境未找到 docker/n8n/comfy 可执行命令，但这不证明用户没有远端或其他方式部署的服务。

本文分三类：**已核实**=当前源码/官方文档明确支持；**需配置/适配**=可以构造，但不能算现成已打通；**待实测**=质量、时间、可靠性与实际兼容尚无执行证据。没有用星数作为效果分数。

## 3. 纠正会影响决策的事实

### 3.1 n8n 已经提供内置 MCP

官方页面明确：支持搜索可见流程、运行/测试已暴露流程、创建与编辑流程及数据表；构建/编辑流程能力注明从2.13.0起提供。execute_workflow默认运行发布版，另有manual模式运行未发布版。客户端需要正确认证、权限和版本；官方未在此证明 LobeHub 与目标 n8n 版本的实际联通。

MCP与REST不能混为一谈：创建流程可走内置MCP/公开API；调用现成流程可走MCP或Webhook；不能假设公开REST存在一个通吃所有流程的任意执行接口。MCP对象暴露与用户可见性仍有范围限制，客户端操作权限与每个流程的对象暴露也不是同一层规则。

因此，组合的基本入口可成为：`LobeHub MCP客户端 → n8n内置MCP → n8n流程 → 外部系统/ComfyUI API`。不必先自研一套庞大通用桥接框架，但身份、回调、输出文件与异常状态仍需验证。

### 3.2 n8n 并非只有节点画布

- SSH节点明确支持执行命令、上传与下载文件。
- Wait节点支持定时、Webhook、表单唤醒；官方描述等待时可将执行数据存入数据库后恢复。
- Error workflow处理失败与通知；不能把“有错误处理”说成 Ferry 独有。
- Queue mode已有主进程/worker、Redis与数据库架构；不能把“支持分布式执行”说成 Ferry 独有。
- 当前RBAC文档区分项目角色与自定义角色：项目角色含Registered Community等版本；自定义实例/项目角色列为Enterprise。不能笼统宣称社区版没有权限，也不能反向认为所有细粒度能力均免费开放。

### 3.3 ComfyUI 已经有可编程执行接口

官方列出 `/prompt` 提交生成图、`/history/{prompt_id}` 查结果、`/queue` 查/管理队列、`/view` 读取图像、`/object_info` 查节点，以及WebSocket执行事件。它不需要依赖人手点击界面才能被外部系统调用。

但提交成功不是产物完成；工作流JSON、模型与插件需要在目标ComfyUI环境实际可用。中断/队列操作是否按目标任务精确隔离、历史与产物的保留、重启后的行为，必须按所装版本验证，不能仅凭路由名称下结论。

## 4. 任务一：把代码变更部署到三台测试主机，并恢复旧版本

### 相同输入与完成标准

测试仓库、固定commit SHA、同一构建脚本、R1/R2两个不可变产物、三台隔离Linux Compose主机、普通配置和秘密变量各一个、测试通知接收端。只测试应用配置/产物恢复，**不测试业务卷数据回滚**；两方案使用相同构建产物和健康检查脚本，避免把外部CI质量差异当平台差异。

成功：准确记录commit/产物hash/目标主机/配置版本；部署结果可查；第二台故意失败后第三台不继续；显式恢复R1时使用当时配置及密钥快照；副作用未知时不盲目重跑。人工确认不得由聊天模型代替。

### 两种方案怎样落地

| 环节 | Ferry | LobeHub + n8n；此任务不需要ComfyUI |
|---|---|---|
| 需求与确认 | 现有会话/页面与平台工具；完整自然语言发布流程仍需配置验证 | LobeHub对话，MCP调用受控n8n流程；实际OAuth/工具结果需联通 |
| 代码与构建 | 仓库连接、Actions式流水线与Runner；不宣称兼容所有Actions | Git平台节点/API + SSH执行相同脚本，或共同引用已有CI结果 |
| 部署目标 | 已有主机/主机组与部署资源 | 在流程中配置SSH/主机列表，或调用已有部署系统 |
| 配置预览与版本冲突 | 已有preview/expected_hash/version检查 | 需要配置生成预览、计算hash、保存待批准输入，执行前再核验 |
| 人工批准 | 操作确认与既有流程人工机制；此处完整串联未实测 | Wait/表单/Webhook等可组合；要绑定确切版本/目标与审批人 |
| 发版执行 | Compose/Docker/native/Swarm领域执行与逐目标结果 | SSH调用部署脚本；脚本或外部部署服务承担引擎语义 |
| 历史恢复 | 已有历史产物、加密变量/配置快照和独立rollback权限 | 需保存版本产物+当时配置，设计恢复流程；不能只重新读取当前凭据 |
| 通知与排障 | 既有执行与通知记录，仍要验证端到端关联 | n8n执行记录+Error workflow；连接聊天和部署日志需传关联ID |

Ferry源码依据：`crates/server/src/deployments/mod.rs:1344` 的rollback入口、`:1360` 的权限、version与hash校验、`:1385` 读取历史版本及配置快照；`docs/guides/deployments-and-transfers.md` 明确主机组首失败停止、已成功主机不自动回滚、历史回滚不使用当前配置。工作区这些逻辑的存在已核查，本次未重跑真实引擎验收。

### 故障对照

| 注入点 | 两方案必须证明什么 | 评估 |
|---|---|---|
| R2预览后修改变量 | 旧确认不得部署新内容 | Ferry已有hash/版本边界；n8n可实现，但需明确保存/比较 |
| 第二台部署失败 | 保留第一台真实结果、第三台跳过，不报全成功 | Ferry已有领域规则；n8n循环/错误分支需按同规则配置 |
| 执行成功但响应断开 | 不因超时就重复部署 | Ferry有请求账本/未知结果防重思路；整个部署链仍待实测；n8n不自动赋予SSH命令幂等性 |
| R1使用的外部秘密已撤销 | 准确报告外部凭据失效，不能承诺历史快照一定可恢复服务 | 两者都不能让撤销的外部凭据重新有效 |
| 服务端重启 | 找回任务与真实目标状态，不能从错误节点盲目重来 | 两者都需要故障注入实测，不由架构图自动证明 |

**判断：Ferry在“可复用的部署领域模型”上有现有资产优势；n8n+脚本在单次简单SSH发布上完全有竞争力。** 若团队已有成熟CI/CD、Ansible或部署系统，n8n接这些系统即可，Ferry的优势会缩小。只有用户确实需要、且愿意使用Ferry的版本/配置/节点管理时，继续投入才有依据。

## 5. 任务二：多个仓库的变化汇总、可追溯报告与通知

### 相同输入与完成标准

三个有权访问的测试仓库、固定UTC日期区间、作者改名/合并提交/重复事件夹具，以及一个失败的数据源。报告包括实际提交/作者/仓库维度和来源链接；缺数据明确标覆盖不足；失败重试不得重复累计或把未同步当零。不将提交数当生产力评价。

| 环节 | Ferry | LobeHub + n8n |
|---|---|---|
| 授权与采集 | 已有仓库连接、轮询/事件、洞察采集范围 | GitHub/GitLab等节点/API与触发；具体平台覆盖逐项验证 |
| 作者身份与历史 | 已有身份映射、持久化采集与查询逻辑 | 简单按作者字符串聚合容易；稳定别名/历史映射需表或自定义服务 |
| 统计查询 | 已有overview/contributors/ranking/repositories/branches/commits/heatmap/period等query类型 | 适合按需拉取后聚合；要稳定长期指标则需定义存储、去重和统计口径 |
| 解释与周报 | 可引用已验证数据；AI解释不是现有统计自动拥有的能力 | LobeHub或n8n模型节点生成摘要与推送，组合适合该场景 |
| 持续产品界面 | 已有工作区洞察页面与数据对象 | n8n主要提供流程与执行；若需要专属可筛选报表UI，需另搭或接BI |
| 发布影响判断 | 本次已查链路未证明“自动判断受影响服务→安全发布”闭环 | 需要仓库/服务依赖、版本与证据，同样不能让LLM凭提交标题保证准确 |

依据：`crates/server/src/repositories/analysis.rs`、`analysis/query.rs:665`、`insights`及身份关联逻辑。`repositories/reports/mod.rs` 当前为退役报告schema兼容模块，不能把旧报告表当现成新产品能力。

**判断：一次性/每周消息汇总，现成组合优先；持续、可筛选、口径稳定的多仓库数据产品，Ferry已有积累。** 不过“有报表”不自动形成竞争力。若用户只需要一条周报消息，不应逼他维护专用洞察平台；若他确实反复查询历史、作者映射和来源覆盖，专属产品才有理由。

## 6. 任务三：通过聊天批量生成图片、审核并交付产物

### 相同输入与完成标准

固定提示词与种子、同一模型及版本、同一GPU、相同尺寸/采样设置、一张经授权输入图、人工审核和同一输出存储。记录图定义、模型/插件版本、prompt_id、产物、失败与取消状态；随机模型即使seed相同也不强行保证跨版本字节一致。

| 环节 | Ferry当前路线 | LobeHub + n8n + ComfyUI |
|---|---|---|
| 聊天与需求收集 | 已有会话；生成交互质量需实测 | LobeHub已有通用聊天/Agent基础 |
| 任务编排 | 自有图引擎、AI调用、资产与人工节点基础 | n8n负责编排、Wait和通知 |
| 专业生成图 | 自研图格式/节点，不兼容全部ComfyUI工作流及社区插件 | ComfyUI原生图、模型与节点生态，目标环境仍须装好依赖 |
| 提交与跟踪 | 专业生成适配与实现覆盖需逐项确认 | HTTP /prompt获取prompt_id，WebSocket或history跟踪 |
| 人工审核与文件 | 可沿用Ferry资产与权限，但完整链未验收 | n8n等待+文件存储/分享；权限与回调关联需配置 |
| 复用社区作品 | 不能把已有ComfyUI图直接当Ferry图执行 | 环境依赖满足时直接复用对应ComfyUI图更自然 |

依据：Ferry README兼容范围、`docs/architecture/workflow-platform-v3.md` 自研/不兼容生态声明；`workflows/media.rs`证明资产管理，不证明已拥有ComfyUI所有采样/模型能力；ComfyUI官方路由及事件文档证明可编程执行。

**判断：以专业媒体生成能力和生态为目标，组合方案明显更值得优先验证。** 用同一模型、GPU和参数时，不因为换成LobeHub入口就提高画质；优势主要是现成图和节点适配。若Ferry也调用同一ComfyUI后端，比较就变成权限/任务/资产体验，不必复制生成内核。

## 7. 搭建成本与维护责任：不虚构工时

| 投入 | Ferry继续自研 | 组合现成产品 |
|---|---|---|
| 第一次做常见集成 | 要维护节点适配和表单；现有扩展规范有边界 | 先查现成节点/流程，常见需求更省开发；缺节点仍需API |
| 复杂部署长期维护 | 已有部署/主机/历史模型可复用；仍需维护各引擎与平台 | n8n可编排，但脚本或外部部署系统必须长期维护，不是零代码 |
| 多系统身份和审计 | 自有域内较集中；不代表天然无漏洞 | 各系统内部可有权限；跨系统用户映射、凭据与关联ID需要设计 |
| 生成生态升级 | 自研节点/模型适配成本持续存在 | ComfyUI生态提供能力，也引入插件冲突、模型和Python依赖维护 |
| 扩展与并发 | Ferry已有分布式/执行基础；真实容量要测 | n8n queue mode已有成熟路径，GPU调度另行配置；不能把worker等同Ferry节点 |
| 用户体验 | 可针对具体任务缩短路径；须用用户测试证明 | 跨页面不一定是问题：流程稳定后用户可只在聊天中操作；构建/排障才常需切换 |
| 商用产品化 | 自有实现更可控，依赖各自许可仍要管 | 自用和对客户提供n8n能力的许可边界不同；不能把内部部署方案直接视为无条件OEM方案 |

“三套服务多”不能直接等于“更难”：如果已有Docker/平台运维，维护几项成熟服务可以比维护自研引擎容易。反之，用户只有一台电脑且只需部署功能时，也不应强迫安装不参与任务的ComfyUI/GPU环境。

## 8. 决策建议

| 真实目标 | 推荐 | 理由 |
|---|---|---|
| 自用AI助手、每周汇总、常见SaaS自动化 | 优先试LobeHub+n8n | 已有能力覆盖广，n8n内置MCP降低桥接投入 |
| 专业图像/视频图和社区工作流 | 优先ComfyUI作生成执行后端 | 生态兼容价值高，不宜重造全部图/节点 |
| 缺少运维平台的小团队，管理仓库/主机/发布 | 优先验证Ferry核心闭环 | 已有领域状态/配置快照/Runner可复用，需证明更省事 |
| 已有成熟CI/CD和运维平台的团队 | 不默认再引入Ferry | n8n接已有系统即可；Ferry必须有额外可量化收益 |
| 商业化统一工作台 | 先定义目标客户与核心任务，再定自研/组合 | 许可、支持责任、维护成本及用户体验均影响选择 |

另一个有价值但尚未验证的候选架构：LobeHub作可选入口，Ferry保管主机/发布/授权状态，n8n处理通用集成，ComfyUI处理专业生成。Ferry现有ferry_discover/ferry_request和工作区API为接入提供基础；这不等于任意外部MCP客户端已经可直接使用，仍需验证外部认证、委托权限、写确认、异步状态与下载授权。避免让四个系统都争当同一任务的主调度器，每条流程指定一个owner，其余作为子执行器。

该候选若被采纳，是对既有“n8n/Comfy能力全面自研”路线的调整，需用户另行确认；本报告不修改ADR、PRD或实现。

## 9. 下一轮真实对照的可执行方案

本轮任务对比已完成，以下是尚未执行的实验规格，不伪造测量数据，也不要求用户现在安排实施。

| 实验 | 执行步骤 | 记录项 | 验收/选择依据 |
|---|---|---|---|
| POC-1 发布 | 准备同一仓库/R1/R2/三主机；分别配置完整链；改变预览后变量；令第二台失败；显式恢复R1 | 环境准备与业务配置分别计时、人工步骤、脚本/适配代码量、版本证据、恢复动作 | 无越权/泄密/重复副作用；结果一致后，比较谁减少团队日常工作 |
| POC-2 洞察 | 三仓库固定数据集，含别名/merge/重复事件/失败源；生成同一报告 | 采集与输出分开计时、统计口径、来源覆盖、重复累计、持久查询体验 | 固定夹具统计一致且缺源明示；只有消息需求时组合方案优先 |
| POC-3 生成 | 相同GPU/模型/种子与图；提交、等待、人工审核、取消和产物下载；重启后查状态 | 环境准备、插件修复、成功率、取消范围、产物追踪、耗时/资源 | 后端等价再比前端；专业生态复用优先，不比较不同模型的画质 |
| POC-X 权限/未知 | 用户退出工作区、撤回凭据、丢ACK、重复回调、进程重启 | 是否阻断、重复次数、可定位的真实状态、恢复步骤 | 权限不绕过；未知不当成功/失败；不能以速度优势抵消正确性失败 |

不预设“Ferry一定赢”的权重或分数。不编造性能阈值。先要求相同功能与正确性，再记录时间与操作成本，结合实际使用频率判断。现有投入视为沉没成本；未来价值来自减少的持续工作，而不是已经写了多少代码。
