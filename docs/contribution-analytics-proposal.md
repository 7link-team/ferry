## 推荐设计（待确认，不是已实现能力）

1. 连接下独立配置分析仓库、分支与历史范围，不要求启用通知。
2. 首次回填所选历史；后续由现有监控变化驱动按分支 SHA 与可达历史增量更新。普通 Git 使用每日 act；平台仓库按需进行轻量分支头对账。
3. 监控事件只标记需要同步，不将有限的事件展示记录作为完整统计事实。
4. API 采集与 act 采集使用相同结果契约，由服务端校验并幂等入库。
5. API 不支持或数据不完整时明确显示能力状态，由配置决定是否启用 act，避免静默切换执行成本。
6. act 缓存仅在执行主机，首次获取所需历史，后续 fetch；无需默认每日全量克隆。

复用 `repository_auth.rs` 的授权刷新、凭据和平台接入；扩展分页与单提交统计读取。当前 `MonitorAccess::commits()` 仅取第一页，不能直接用于历史分析。

提交事实按工作空间、仓库、SHA 幂等保存；分支可达关系单独保存。记录采集来源、完整性、错误、同步断点及统计规则版本。完整采集成功后推进断点；历史改写重新核对受影响分支。

需要进一步设计：同仓库通过多个连接接入时的身份归一、读取权限、连接撤销后的访问控制、结果导入授权、历史范围扩大与规则修改后的重算。

## 源码中已识别的重复工作与正确性风险

以下基于固定版本源码。第 2、3 项另用内存 SQLite 最小模型验证了 SQL 语义，尚未通过运行上游服务复现完整流程。

1. `handle.go` 检查分支最新非合并提交及提交数；变化后重新遍历起始时间以来的历史，调用 `ReplaceCommitLogs` 删除再插入。不是逐个新 SHA 采集。
2. 固定版本 `db_commit_filter.go:97` 的 `DeleteQuery` 使用 IsMerge，调用方传入 `IsMerge="0"`，删除仅针对非合并记录；`AnalyzeBranchCommitLogs` 没有按该条件过滤，仍重新插入合并记录，且表缺少对应唯一约束。最小模型连续替换两次后，普通提交 1 条、同一合并提交 2 条。这是重复记录的具体风险路径，但不能据此认定已定位用户实例的全部耗时原因。
3. 同一 SHA 在不同分支重复存储和计算差异。排行/趋势部分查询做 DISTINCT，热力图则 COUNT DISTINCT 但直接 SUM 行数，跨分支行数存在重复累计风险。
4. 更新检测忽略合并提交，即使远端分支头发生纯合并变化，最新非合并 SHA 与数量也可能不变，导致跳过。
5. 时间筛选使用 committer_date，日周月/热力图分桶却使用 author date；这属于需明确展示的口径差异，不能静默统一。周边界与时区也需固定样例核对。
6. `GetCommitDiff` 对合并提交累加相对所有父提交的差异，而语言统计只相对第一父提交；平台 API 的合并提交统计不保证采用同一口径。需要逐父 compare 或 act 计算，不能直接宣称 API 与原结果完全等价。

最小 SQL 模型结果：同一普通 SHA 分别属于 main 与 feature，单次增删行为 10/2、有效值 8；原热力图聚合得到提交数 1、增删行 20/4、有效值 16。建议统一按筛选后的提交集合聚合，修复行数重复，不改变每提交指标定义。

## 初始化与历史范围

- 默认所有分支，包括初始化之后新增的分支；“全部分支”指当前授权可见的分支，未拉取的已删除分支或不可达历史不能凭空恢复。
- 完整历史选中：初始化从所有分支回溯全部可达历史，去重采集；后续仍为增量，不每天重做全量。
- 完整历史未选中：以初始化时刻减去配置天数，持久化固定起点；之后持续累积，不自动把旧记录按滚动窗口删除。
- 查询时间筛选独立于采集范围，“全部”表示已经采集的完整范围；页面应显示覆盖起点与缺失状态。
- 之后扩大历史范围或改为完整历史：只回填尚未覆盖部分，复用已有提交事实；缩短查询范围无需重新采集。
- 采集启动前先建立可靠的增量接收状态；回填结束与远端最新分支头再次对齐，防止初始化期间的推送遗漏。
- 提交时间不保证沿父链单调，不能遇到一条早于起点的提交就盲目停止整个遍历；各平台时间查询语义需要验证。

## 监控驱动增量：无需第二套历史扫描器

复用现有监控入口和授权，但不能仅消费通知历史表：

- 当前 push 入口按 `config.events` 和仓库通知选择过滤；poll 快照也仅在选中 push/branch 时读取分支。分析需要独立订阅分支变化，实际采集范围取通知与分析订阅的并集，通知行为保持原样。
- 验签、权限与配置版本校验成功后，在同一数据库事务中持久化待同步状态；push 的确认响应不能早于可靠落盘。poll 需要将分支快照更新与分析任务入队放在同一事务，避免基线已前移而任务丢失。
- 事件按仓库/分支合并到最新目标版本，批量推送不会逐条触发全仓库分析。同步任务只记录脏版本与进度，不能只靠进程内回调。
- 同仓库任务使用可续期数据库租约和版本栅栏；任务期间又有事件时不得覆盖新脏版本，完成后继续追赶。
- 监控事件的提交列表只是线索，必须按固定目标 SHA 获取完整历史差集；不依赖展示条数和 webhook 提交列表的完整性。
- 首次 push 模式、漏 webhook、服务停机、授权恢复等情况下，仅靠事件无法保证完整。建议复用已有监控的低频分支头核对，发现不一致才入队，不周期遍历所有提交。具体频率属于待定配置。
- 主动轮询模式直接复用其分支快照，不再重复列仓库/分支。普通 Git 没有此平台监控入口，沿用每日 act 更新。

因此可以取消 gitinsight 式独立周期历史分析，但仍需可恢复的任务消费者，以及针对事件遗漏的轻量核对；如果彻底禁止核对，必须接受漏事件导致统计不完整的限制。

## 提交只分析一次，分支关系独立维护

推荐数据边界：仓库身份、分支版本、提交元数据/父关系、提交分析事实、分支可达关系、作者映射、同步任务/覆盖状态。具体表名与迁移方式在实施设计时确定。

- 提交身份唯一键包含工作空间、稳定仓库身份、SHA；分析结果记录规则版本，以数据库唯一约束、版本校验与幂等写入共同防重。规则升级不得混合发布不同版本结果，具体迁移方式在实施时确定。
- 多分支共享 SHA 只计算一次差异；新分支指向已分析提交时，仍需建立分支历史关系，不能因为 SHA 已存在就漏掉分支统计。可复用已保存父图与覆盖信息。
- 先确定筛选分支所对应提交集合，再聚合；仓库/贡献者总览对分支并集去重，逐分支报表分别计算。同一 SHA 出现在三个分支时总览计一次、每个分支各计一次；不能把分支报表直接相加作为总览。
- cherry-pick/rebase 后不同 SHA 仍按不同提交保留，不能擅自按补丁相似度合并贡献。
- force push/分支删除只调整受影响的可达关系并保留原始事实；默认报表是否保留已不可达贡献需单列产品决策，不能未经确认改变历史。
- API 请求优先获取轻量 SHA/父关系，只有未完成分析的 SHA 才取统计明细；支持批量 stats 的平台可优化首次回填。限流遵循服务端提示，失败重试只补缺口。
- 不完整结果不能标记为完成；API 字段缺失、截断、父提交语义不等价时补充 compare/diff，必要时交 act 保证原功能。
- 原始分析事实与作者映射、聚合缓存分开；改昵称/筛选条件不重新访问 Git。聚合先使用索引查询，实测瓶颈后再增加增量汇总，不能先引入重复计数缓存。

## 可复现实验（2026-11-02）

命令：`python -X utf8 scripts/research-contribution-analytics.py`，结果 PASS。

实验仅在自动清理的临时目录构建 Git 历史，使用内存 SQLite，不访问用户仓库或私有凭据，不运行 Ferry 或上游服务。

- 5 个独立提交对应 12 个分支出现次数，证明按分支逐次分析的重复成本。
- 新分支指向已知提交时新增分析数为 0，仍有 2 条可达关系需要建立。
- 一次新推送只新增 1 个 SHA；历史改写和删除分支后可识别 4 个已不可达提交。
- 同一 merge 所有父提交差异新增 5 行，第一父提交差异新增 3 行，不能将平台默认 stats 无条件当作兼容值。
- 作者日期与提交者日期不同的提交保留两类时间。
- 替换 SQL 模型复现 merge 记录重复；热力图 SQL 模型复现提交数 1、行数重复累计为 20。
- 验证逐提交有效值之和为 10，而汇总净增后截零为 2，两种算法不能替换。

具体实施边界与验收计划见 `docs/contribution-analytics-implementation-plan.md`。
