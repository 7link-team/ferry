## 1. 结论摘要

1. **两种定义，一个平台**：
   - **流水线**（Pipeline，沿用 v2，Actions YAML）承接研发交付，对标云效 Flow。
   - **工作流**（Workflow，新增，图 JSON）承接通用自动化和 AI 内容生产，对标 n8n 和 ComfyUI。

   两者共用一层外壳，包括：触发、凭据、版本与发布、执行租约与队列、人工节点、执行记录、资产与产物、通知、权限、成本。
2. **把 n8n 和 ComfyUI 合成一个图引擎，而不是做两个**：
   - 统一的数据单位是**条目**（item = JSON + 二进制资产引用），这是 n8n 的模型；
   - **端口类型**（文本、图像、视频、音频……）是加在条目上的约束和展示层，这是 ComfyUI 的类型化连线；
   - 每个节点声明自己的**运行位置**：服务端、主机或 GPU worker。

   这样，一张图里可以同时有 HTTP 调用、LLM、图像生成和 ffmpeg 合成。
3. **ComfyUI 部分完全自研**：
   - 图编辑器、类型校验、按输入签名缓存、队列/进度/预览、问题面板、模型库、资产库，都在 Ferry 内实现；
   - 生成能力分两条路：
     - **云端模型 API 节点**，先做；
     - **自研 Python 推理 worker**，后做，跑在 GPU 主机上，由 Runner 托管，基于 PyTorch / diffusers / transformers 这类许可宽松的库。
   - **不复制 ComfyUI 的代码**（GPL-3.0），也不兼容它的工作流 JSON 和自定义节点。
4. **n8n 部分完全自研**：
   - 条目数据流、控制节点、沙箱代码（JS 在服务端，Python 在主机）、HTTP、Webhook 同步回应、等待与表单、子工作流、LLM/Agent、集成节点；
   - 集成节点用**声明式节点规范**分批补齐，长尾集成用 HTTP 节点加凭据模板覆盖；
   - **不使用 n8n 代码**（Sustainable Use License 不允许商业分发）。
5. **与 v2 的融合点**：
   - v2 P0（执行租约、并发、定义版本）在实现时**直接做成两种定义共用**，这是 v3 对 v2 唯一的改动要求（§11）；
   - 流水线可以作为工作流里的一个节点（“运行流水线”）；
   - 工作流也可以由流水线事件触发。
6. **分期**：
   - v2 P0（改为共用设计）→ **S0 共用外壳** → S1 数据流引擎 MVP → S2 AI 文本与集成第一批 → S3 AI 媒体（云端） → S4 本地 GPU 推理 → S5 场景模板与集成扩充；
   - v2 的 P1/P2 与 S1–S3 并行推进。
7. **诚实边界**：
   - “n8n 能做的都要有”是一张**按对标清单逐项交付的路线图**，不是一个版本能完成的事。第一批集成不会有 400 多个，靠声明式规范分批补。
   - “ComfyUI 能做的都要有”指**功能覆盖**：编辑、执行、缓存、生成能力。不包括数千个社区节点的生态。
   - 本地推理的模型种类，按 S4 选定的模型族逐步增加。

## 3. 设计原则（在 v2 §5.3 基础上增补）

- **P-6 一个图引擎**：n8n 式数据流与 ComfyUI 式生成图共用同一种格式、同一个引擎、同一套编辑器，以条目为唯一的数据载体。不做两套图系统。
- **P-7 运行位置是节点属性**：节点在服务端、主机还是 GPU 上运行，由节点类型和节点设置决定，引擎负责调度与数据搬运。用户画的是业务图，不是部署图。
- **P-8 大数据不进数据库**：条目中的 JSON 有大小上限；文件、图像、视频一律以**资产引用**（内容哈希）传递，存放在 `ArtifactStore`（v2 §11.1，local/S3）中。
- **P-9 副作用节点必须可追溯，纯节点才可缓存**：节点声明 `pure` 或 `side_effect`：
  - 纯节点按输入签名缓存；
  - 副作用节点使用“先写意图”的幂等机制（v2 §8.5），永不自动跳过。
- **P-10 不复制受限许可的代码**：n8n（Sustainable Use License）和 ComfyUI（GPL-3.0）只作为行为参考，不复制、不改写它们的源代码，节点规范与文件格式均为自有设计。

## 5. 共用外壳（S0）

### 5.1 定义与版本

- **资源**：
  - `pipelines`：已有；
  - `workflows`：新增，形状同标准资源，有统一信封和 `version` 字段。
- **版本**：
  - v2 P0 中的 `pipeline_revisions`，在实现时改为通用的 `definition_revisions(subject_kind, subject_id, number, definition, …)`，其中 `subject_kind` 取 `pipeline` 或 `workflow`（§11）。
  - 草稿与发布按 D16：保存产生草稿版本；“发布”把某个版本设为 `published_revision_id`；事件、定时、Webhook 生产地址只使用已发布版本；手动运行和测试运行可以用草稿。
- **模板**：`pipeline-templates` 已经按 `engine` 区分格式，新增 `engine: "ferry-graph"`。资源名保留，界面上统称“模板”。

### 5.2 触发中心

触发器有两类：

- **派生触发器**：保存定义时由定义推导出来，存入**通用表** `trigger_bindings`（即 v2 的 `pipeline_triggers` 通用化，增加 `subject_kind`）。
- **注册式触发器**：Webhook 路径、表单地址、聊天入口，需要对外注册。

| 触发 | 流水线 | 工作流 | 实现 |
|---|---|---|---|
| 手动（可带参数） | ✔ | ✔ | `create_run` / `create_execution` |
| 定时 | ✔（cron_jobs） | ✔：**定时触发节点是唯一的事实来源**，保存工作流时在同一事务内派生出 `cron_jobs` 行（标记为“由工作流管理”，在定时任务页只读）。这遵循 v2 P-1，与 D3“只保留一处可编辑”的意图一致 | 复用 `cron_jobs.rs` 的调度与执行 |
| 代码事件（推送 / MR / Tag） | ✔ | ✔ | v2 的 TriggerEvent + 发件箱，发件箱行增加 `subject_kind` |
| 通用 Webhook | ✔（D17，只能异步） | ✔：测试 / 生产两种地址，可同步回应 | 新表 `webhook_endpoints` |
| 表单 | — | ✔ | 表单定义来自触发节点；公开页面由服务端渲染（§9.6） |
| 聊天 | — | ✔ | 聊天会话页 + 消息触发（S2） |
| 上游完成（流水线或工作流） | ✔ | ✔ | 执行结束事件写入发件箱 |
| 应用事件（轮询型集成触发器） | — | ✔ | 集成节点声明 `poll`，复用轮询租约模式（`polling.rs`），S2 |
| 错误触发（某工作流失败时运行另一工作流） | — | ✔ | 执行结束事件 |

**同步回应 Webhook**：

- 只用于工作流的生产地址。接收请求的实例**就地**创建并执行这次执行，执行租约归本实例，不进入公共队列，直到遇到“回应 Webhook”节点或执行结束；
- 超时（默认 30 秒，可设 1–300 秒）后回应 504，执行本身继续；
- 回应模式三选一：立即回应、最后一个节点结束后回应、由回应节点决定，对标 n8n。

### 5.3 执行队列与租约

v2 §8.2–8.4 的执行级槽、租约、栅栏、挂起与唤醒、接管，**同时用于 `pipeline_runs` 和 `workflow_executions`**：

- 两张表都有同样的租约列；
- 调度器按 `subject_kind` 分派给对应的编排者（`RunOrchestrator` 或 `GraphExecutor`）；
- 执行级槽分开计数：`FERRY_PIPELINE_MAX_RUNS` 与 `FERRY_WORKFLOW_MAX_EXECUTIONS`（默认 16，工作流的执行大多很轻）；
- 同步 Webhook 执行**不占**公共槽，另有上限 `FERRY_WEBHOOK_MAX_INFLIGHT`（默认 64），超出时回应 503。

### 5.4 人工节点（审批 / 表单 / 挑选）

把 v2 的审批任务推广为**人工交互**。它在两种定义里通用：流水线中是 `ferry-task: approval|form`，工作流中是“人工”类节点。

| 类型 | 交互 | 产出 |
|---|---|---|
| 审批 | 通过 / 拒绝 + 意见（v2 §13.1 全部规则：审批人、会签、超时、自审） | `decision`、`comment` |
| 表单 | 字段：文本 / 长文本（Markdown）/ 数字 / 选择 / 日期 / 文件上传 / 多值；可预填上游数据 | 一个条目 |
| 挑选 | 从上游条目（含图像、视频、音频、文本）中选择 N 个，可附评分和修改意见；可选“全部不满意，重做” | 被选中的条目 + `redo` 标志 |
| 编辑 | 在线编辑上游文本（如章节正文）或 JSON，提交修改后的版本 | 修改后的条目 + 差异 |

- **入口**：
  - 执行详情；
  - “待我处理”列表；
  - 通知里的链接；
  - 外部链接（带一次性 token，适用于不登录的外部审阅者）。外部链接是否开放由 V9 决定。
- **存储**：v2 的 `pipeline_run_approvals` 通用化为 `human_tasks` 与 `human_responses`，增加 `subject_kind`、`kind`、`form_schema`、`response`（加密）。
- **挂起与唤醒**：复用 v2 §8.1 的 `waiting` 与 `not_before`。

### 5.5 资产库

- **资产**：内容寻址（sha256），存放在 `ArtifactStore` 中，**S0 就需要**，因为工作流的二进制数据从第一天起就走资产引用。服务端模块命名为 `content_assets`，因为 `assets.rs` 已被嵌入前端的静态资源服务占用。
- **与流水线产物的关系**：两者只共用 `ArtifactStore` 的存储后端（local/S3）。**流水线产物保持 v2 的路径寻址**（`artifacts/{run}/…`，重跑时复制，D9），不改为内容寻址；内容寻址只用于 `assets`。
  - 这使 v2 的 D2（S3 兼容存储）从 P2 提前到 S0；
  - 本地存储仍是默认。
- 表 `assets`：
  - `id`、`workspace_id`、`sha256`、`size`、`mime`、`kind`（image/video/audio/text/file/model）；
  - `width`、`height`、`duration_ms`、`thumbnail_asset_id`；
  - 来源字段 `execution_id`、`node_id`；
  - `pinned`、`created_at`；标签存在关联表 `asset_tags(asset_id, tag)` 中，以便建索引。
  
  同一工作空间内，相同哈希只存一份。
- **缩略图与元数据**：
  - 图像在服务端生成缩略图，用 `image` crate（纯 Rust，MIT/Apache），并设置 `Limits` 防解压炸弹；
  - 视频和音频的缩略图与时长，**在资产产生时立即**由产生它的主机节点或 GPU worker 计算并随结果回传，因为下游表达式可能要用到时长（如按配音长度裁剪镜头）；
  - 主机上需要 ffmpeg（V8），服务端不引入 ffmpeg 依赖。
- **界面**：资产库页面，可按类型、标签、来源执行筛选；网格预览；右键菜单：插入到工作流、下载、查看来源执行、以来源执行的参数打开（对标 ComfyUI）。
- **保留**：
  - 被执行引用的资产，随执行一起按 `history_retention_days` 清理；
  - 用户“固定”的资产不清理；
  - 每个工作空间有资产配额，默认 50 GiB，可在平台设置中调整。

### 5.6 成本

- 每个节点执行时记录成本，写入 `cost_records(execution_id, node_id, provider, model, unit, quantity, amount_micros, currency)`。
  - `unit` 可以是 `input_tokens`、`output_tokens`、`seconds`、`images`、`video_seconds`、`characters` 等；
  - 价格来自凭据上配置的单价表，单价由用户填写，平台不内置价格。
- 执行详情显示总成本和逐节点成本；工作流统计显示成本趋势。
- **预算**：工作空间级的月预算，可选；超出后新的 AI 节点执行直接失败，原因写“已超出本月 AI 预算”。

### 5.7 统一执行视图

- 菜单“执行”合并显示流水线执行与工作流执行：
  - 列：类型、名称、编号、状态、触发、耗时、成本、开始时间；
  - 筛选：类型、状态、触发、版本、待我处理。
  
  这一页依旧是统一列表组件的配置，后端由一个只读聚合接口 `GET /executions` 提供，用 `UNION ALL` 实现标准分页，见 §12.2。
- 队列视图：运行中 / 排队（附原因）/ 等待人工，可取消。

## 6. 工作流图引擎（S1）

### 6.1 图格式（`engine: "ferry-graph"`）

`workflows.definition` 存 JSON：

```jsonc
{
  "engine": "ferry-graph",
  "schema": 1,
  "nodes": [
    { "id": "n_webhook", "type": "core.trigger.webhook", "type_version": 1, "name": "接收需求",
      "params": { "path": "story", "method": "POST", "respond": "on_last_node" },
      "position": [0, 0] },
    { "id": "n_llm", "type": "ai.llm.chat", "type_version": 1, "name": "扩写剧本",
      "params": { "model": "qwen-max", "prompt": "={{ '根据以下梗概写剧本：' + $json.body.idea }}",
                  "response_format": "json", "json_schema": { "type": "object" } },
      "credentials": { "provider": "8801" },
      "settings": { "retry": { "max_tries": 3, "wait_ms": 2000 }, "on_error": "stop",
                    "cache": "auto", "runtime": null, "mode": "active", "notes": "" },
      "position": [320, 0] }
  ],
  "connections": [
    { "from": { "node": "n_webhook", "port": "main", "index": 0 },
      "to":   { "node": "n_llm",     "port": "main", "index": 0 } }
  ],
  "layout": { "groups": [ { "id": "g1", "title": "剧本", "color": "blue", "nodes": ["n_llm"] } ],
              "notes": [ { "id": "s1", "text": "…", "position": [0, 200] } ],
              "reroutes": [] },
  "settings": { "timezone": "Asia/Shanghai", "timeout_seconds": 0, "error_workflow_id": "",
                "save_data": { "success": "all", "error": "all", "manual": true, "progress": false },
                "concurrency": { "scope": "workflow", "policy": "queue", "max_parallel": 4 } },
  "pin_data": { "n_webhook": [ { "json": { "body": { "idea": "…" } } } ] }
}
```

| 字段 | 规则 |
|---|---|
| `nodes[].id` | `^[a-z][a-z0-9_]{0,63}$`，在一个图内唯一，**不可改**（改名只改 `name`）；连线、缓存、执行记录都按 id 关联 |
| `nodes[].type` / `type_version` | 来自节点注册表。节点类型升级时，旧版本照常可用；编辑器提示“有新版本”。版本迁移函数由节点实现提供，用户确认后才执行，对标 n8n |
| `params` | 由节点的参数 schema 校验。以 `=` 开头的字符串值是**表达式**（§6.4） |
| `credentials` | 键是节点声明的凭据槽，值是凭据 ID，必须属于本工作空间且类型匹配。凭据**不进入条目数据，也不进入日志** |
| `settings.mode` | `active`（启用）、`bypass`（透传：输入原样输出）、`mute`（跳过：不执行，下游视为没有输入） |
| `settings.runtime` | 运行位置，详见 §6.5。`null` 表示使用节点默认位置 |
| `settings.cache` | `auto`（纯节点默认缓存）、`off`、`force_refresh`（本次执行忽略缓存但写回）。副作用节点只能为 `off` |
| `pin_data` | 测试时固定的输出数据，**只对手动或测试执行生效，生产执行忽略**（与 n8n 一致） |
| 大小 | 定义 ≤ 2 MiB，节点 ≤ 500 个，`pin_data` ≤ 1 MiB（超出时提示改用资产） |

### 6.2 条目（数据载体）

```jsonc
// 一个条目
{ "json": { "title": "第 3 章", "words": 3200 },
  "binary": { "cover": { "asset": "sha256:…", "mime": "image/png", "name": "cover.png", "size": 812345 } },
  "paired": { "node": "n_split", "index": 2 } }   // 条目溯源，用于 Merge 按来源配对、表达式取上游数据
```

- 节点的每个端口接收和输出**条目列表**。
- 每次执行的条目 JSON 有上限：单个条目 ≤ 1 MiB，单个节点输出总和 ≤ 16 MiB，超出时节点失败，提示改用二进制资产。
- `binary` 只存资产引用，二进制内容在 `ArtifactStore` 中。

### 6.3 端口类型（融合 ComfyUI 的类型化连线）

| 端口类型 | 含义 | 连线颜色 | 校验 |
|---|---|---|---|
| `main` | 任意条目（n8n 默认） | 灰 | 可以连接任何非内部类型 |
| `text` | 条目中 `json.text` 必须存在 | 绿 | 可以连接 `main`，也可以连接 `text` |
| `image` / `video` / `audio` / `file` | 条目必须带有对应 mime 的 `binary.data` | 蓝 / 紫 / 橙 / 棕 | 可以连接 `main`，运行时校验 |
| `json<schema>` | 条目 JSON 满足声明的 schema（例如“分镜列表”） | 黄 | 编辑器做静态提示，运行时校验 |
| `model` | 模型引用（`models` 表 ID） | 红 | 只能连接 `model` |
| `gpu:*`（latent、conditioning、模型句柄……） | **GPU worker 内部类型**，只在同一 GPU 分段内传递（§8.3） | 深色 | 只能在 GPU 节点之间连接；跨分段连接在保存时拒绝 |

- **编辑器行为**（对标 ComfyUI）：
  - 拖线时只高亮兼容端口；
  - 松手在空白处时，弹出按类型预筛的节点搜索；
  - 节点面板可以按输入 / 输出类型筛选；
  - 连不兼容的端口时**给出提示**，说明原因（ComfyUI 不提示，这里做得更好）。
- `main` 与具体类型之间可以互连，保证 n8n 式的“任意数据”工作流不受类型约束；类型只在声明了的端口上生效。

### 6.4 表达式

- **语法**：参数值以 `=` 开头，模板内 `{{ … }}` 是 **JavaScript 表达式**，在服务端 JS 沙箱中求值（§7.2），语义对标 n8n。
- **上下文**：

| 上下文 | 内容 |
|---|---|
| `$json` / `$binary` | 当前条目 |
| `$input.all()` / `.first()` / `.item` | 当前节点的输入条目 |
| `$('节点名').item` / `.all()` | 按条目溯源取上游节点数据 |
| `$node` | 当前节点 |
| `$execution.id` / `.mode` / `.resumeUrl` | 执行信息 |
| `$workflow` | 工作流信息 |
| `$vars` | 工作空间 plain 变量 |
| `$now` / `$today` | 时间，带时区 |
| `$env` | **不提供**，主机环境变量不暴露 |

  `secrets` 不能在表达式中直接引用。密钥只能经由节点声明的凭据槽使用，这条规则与 v2 D1 的服务端表达式规则一致。
- **与流水线表达式的关系**：流水线（Actions YAML）继续使用 Actions 表达式，由 v2 D1 的 worker `evaluate` 求值；工作流使用 JS 表达式。**两种定义各自沿用其对标产品的语言**，不强行统一。这一点作为 V3 记录。
- **编辑器**：表达式编辑器提供补全（上游字段、方法）和实时预览，对标 n8n 实测的 `[invalid syntax]` → `144`。

### 6.5 运行位置

| 运行位置 | 适用节点 | 执行方式 |
|---|---|---|
| `server`（默认） | 控制、转换、HTTP、LLM 与云端模型 API、集成、JS 代码、人工节点 | 在服务端进程内执行。JS 进入沙箱；网络请求走出站策略（§7.3） |
| `host` | 命令、Python 代码、ffmpeg 合成、文件处理、“运行在主机上的 CLI 工具”（如编程代理） | 通过 `HostChannel.exec_stream` 在选定主机上执行，主机由节点设置的 `target_kind/target_ref` 决定，规则同 v2 的执行目标。输入条目和资产经文件传输上传，输出回收为条目和资产 |
| `gpu` | 本地推理节点 | 在选定 GPU 主机的 `ferry-infer` 守护进程中执行（§8） |

- **数据搬运**：引擎负责搬运。服务端与主机之间只传条目 JSON 和**用到的**资产：
  - 同一主机上连续执行的节点，资产不重复下载（主机端有按 sha256 命名的本地缓存目录）；
  - 主机产出的文件按 sha256 去重后回收。
- **调度**：主机和 GPU 节点占用 v2 的主机任务槽；GPU 节点另外占用 GPU 槽（§8.4）。

### 6.6 执行语义

1. **执行计划**：先确定目标集合，再取目标的上游闭包作为待执行节点，最后做拓扑排序。目标集合按执行方式确定：

| 执行方式 | 目标集合 |
|---|---|
| 完整执行 | 触发器下游的所有终点节点 |
| 执行到此节点 | 选中节点，对标 ComfyUI 的“执行到选定输出” |
| 从此节点重跑 | 选中节点及其下游；上游使用父执行的输出或固定数据，对标 n8n 的单步执行 |

2. **调度顺序**：就绪节点并发执行，每次执行的并发上限默认 8。多输入节点（如 Merge）的输入顺序按端口序号确定，**结果与执行快慢无关**。
3. **单次处理与逐条处理**：节点声明 `batch`（一次处理全部条目）或 `per_item`（逐条处理）。逐条处理的节点可以设置“条目并发”，默认 1，云端 API 类节点默认 4。
4. **分支**：If / Switch 的未命中分支不产生条目，其下游节点**不执行**（不是失败）。下游 Merge 节点的规则：
   - 至少一个输入有条目就执行；
   - 也可以设为“等待全部输入”。
5. **循环（结构化，不允许画环）**：用**循环容器**节点，里面放子图。

| 循环模式 | 执行方式 | 用途 |
|---|---|---|
| for-each 并行 | 每个条目执行一次子图，有并发上限 | 逐镜头生成 |
| for-each 顺序 | 逐个执行，可以设置**携带状态**：上一轮的输出作为下一轮输入的 `$carry` | 逐章写作，带前文摘要 |
| while | 每轮执行后求值条件，有最大轮数（≤ 1000） | 评审不通过就重写，最多 N 次 |

   循环容器在画布上是一个可展开的框。每一轮的节点执行记录带上**轮次路径**，例如 `loop1[3].n_llm`，执行详情里可以按轮次查看。
6. **失败处理**（节点通用设置，对标 n8n 实测）：
   - 自动重试：次数和间隔可设；
   - 失败后可选择：
     - 停止执行；
     - 继续，错误信息作为条目输出；
     - 继续，走**错误输出端口**；
   - “始终输出”：没有条目时输出一个空条目；
   - “只执行一次”：只处理第一个条目。
7. **纯节点缓存**（对标 ComfyUI 实测，并修正它的缺点）：
   - 缓存键 = `sha256(节点类型@版本 + 规范化 params（表达式求值之后）+ 输入条目的规范化 JSON + 输入资产哈希 + 所用模型哈希 + 凭据的“缓存分区”)`；
   - 凭据只按 ID 参与，**不参与内容**；同一凭据在同一工作空间内共享缓存，**不跨工作空间**。
   - 命中时直接取回输出，节点在画布和执行详情中标为“**缓存命中**”（附原执行链接）。ComfyUI 实测在画布上完全不标识命中，这里必须做到。
   - 节点是否纯，以 §18.9 的纯度表为准；缓存键的完整定义也以 §18.9 为准。
   - 缓存表 `node_cache(key, workspace_id, node_type, outputs_ref, size, created_at, last_used_at)`，按工作空间配额加 LRU 淘汰，默认 20 GiB，资产引用计数。
8. **等待与人工**：遇到等待、人工、Webhook 回调类节点时，执行挂起，复用 v2 §8.1：释放槽位，`not_before` 设为最近的唤醒时刻。唤醒后从挂起节点继续，**已完成节点的输出从执行数据中恢复**，不会重新执行。
9. **持久化与恢复**：
   - 每个节点完成后，把它的输出写入 `workflow_node_runs`，大于 64 KiB 的部分转存为资产引用。执行数据的保存策略按工作流设置（对标 n8n“保存哪些执行”）。
   - 编排者丢失时，接管方按 v2 §8.4 的规则处理：
     - 已完成的节点直接复用；
     - 运行中的纯节点重新执行；
     - 运行中的副作用节点按“意图”记录判定（v2 §8.5），无法判定时标为失败，原因 `orchestrator_lost`。
   - 同步 Webhook 执行遇到接管时不能再回应（连接已经断开），这一点在设计上接受，并记录到日志。
10. **固定数据与测试执行**：手动执行时，固定了数据的节点不执行，直接使用固定数据；生产执行忽略固定数据。测试执行在执行列表中带“测试”标记，对标 n8n 的 🧪。
11. **子工作流**：“执行子工作流”节点有两种模式：
    - 一次性传入全部条目；
    - 逐条执行。
    
    子执行是独立的执行行，带 `parent_execution_id`，调用深度 ≤ 10。等待子执行时，父执行挂起。被调用方可以设置“谁能调用我”：任意本空间工作流，或者指定列表（n8n 2.45.7 实测找不到这项设置，Ferry 补上）。

### 6.7 执行状态

| 对象 | 状态 |
|---|---|
| 执行 | `queued` / `running` / `waiting` / `succeeded` / `failed` / `cancelled`，加 `end_reason`，沿用 v2 |
| 节点执行 | `pending` / `running` / `succeeded` / `failed` / `skipped`（分支未命中或静音）/ `bypassed` / `cached` / `pinned` / `waiting` |

- 每条节点执行记录：开始和结束时间、输入输出条目数、成本、轮次路径、尝试次数、缓存键。
- 取消与失败分开显示，ComfyUI 实测把中断显示为失败，这里不这样做。

## 7. 节点体系

### 7.1 节点注册表与规范

每个节点类型提供一份**节点规范**，编辑器和服务端共用：

```jsonc
{ "type": "ai.llm.chat", "version": 1, "category": "AI/文本", "display": { "name": "LLM 对话", "icon": "sparkles" },
  "runtime": { "default": "server", "allowed": ["server"] },
  "purity": "side_effect",                    // pure | side_effect；LLM 默认 side_effect（即使 temperature=0，服务端也不保证结果确定），用户可在节点设置中显式开启缓存，见 §18.9
  "item_mode": "per_item",
  "inputs":  [ { "port": "main", "type": "main" } ],
  "outputs": [ { "port": "main", "type": "text" } ],
  "credentials": [ { "slot": "provider", "types": ["llm.openai_compatible", "llm.anthropic", "llm.dashscope"] } ],
  "params": { /* JSON Schema + UI 提示（控件、条件显示、可否使用表达式）*/ },
  "cost": { "units": ["input_tokens", "output_tokens"] } }
```

- 节点规范由服务端通过 `GET /node-types` 提供，编辑器据此渲染参数表单。参数表单直接用 AutoForm 的配置渲染，符合“表单都由共享组件配置”的项目规则。
- **实现方式有三种**：

| 实现方式 | 说明 | 适用 |
|---|---|---|
| Rust 原生 | 服务端内置实现 | 核心节点：控制、转换、HTTP、人工、AI 文本、云端媒体 |
| **声明式** | 只有一份 JSON 规范：凭据类型、操作列表，每个操作是 HTTP 请求模板加响应映射。由一个通用执行器执行，**不写代码** | 大部分 SaaS 集成（§7.4） |
| 主机脚本 / GPU | 节点规范 + 主机端或 worker 端实现 | ffmpeg、文件处理、本地推理 |

### 7.2 代码节点

| 语言 | 运行位置 | 隔离与限制 |
|---|---|---|
| JavaScript | **QuickJS**（`rquickjs`，MIT），进程模型见 §18.12（V13：推荐独立的低权限沙箱进程）。Windows（MSVC）构建尚未验证，S1 第一项工作就是做这个验证 | 每次求值单独创建运行时（不跨租户共享堆）；内存 ≤ 128 MiB，执行时间 ≤ 30 秒（可设到 300 秒）；整个进程有全局内存预算；没有文件和进程能力；网络只能通过 `$http`，受出站策略约束；没有 Node 内置模块和 npm |
| Python | **只在主机上运行**（运行位置 `host`），用主机上的 Python | 由主机自身隔离。服务端不嵌入 Python，保持单二进制和桌面形态（V4） |

### 7.3 出站网络策略

- 服务端节点（HTTP、集成、云端模型，包括 `$http` 和 `llm.openai_compatible` 的 `base_url`）的出站请求，统一走一个**新建的出站客户端**。现有的告警投递客户端完全禁用重定向（`alerts.rs:613`），也没有地址过滤，不能直接复用。新客户端的要求：
  - 先解析域名，再**固定 IP** 发起连接，防止 DNS 重绑定；
  - 默认拒绝私有、回环、链路本地、元数据地址（含 `169.254.169.254`、IPv6 和 IPv4 映射地址）；
  - 允许跟随重定向（最多 5 次），**每一跳都重新做地址检查**，跨域时去掉认证头；
  - 超时和响应体上限（默认 50 MiB）可配置。
- **内网放行只能由平台管理员配置**（平台设置），不能由工作空间自行配置。否则就等于把平台所在网络开放给任意租户。
- 主机节点的网络由主机决定，平台不干预。

### 7.4 节点目录（按期）

| 类别 | 节点 | 期 |

## 8. AI 引擎平面（S3 云端 / S4 本地）

### 8.1 云端生成（S3）

- 节点运行在服务端，提交任务给服务商，服务商通常是异步任务：
  - 节点进入 `running`，每 5–15 秒轮询一次，或者使用服务商回调；回调走 `webhook_endpoints`，地址带一次性 token；
  - 下载结果后存入资产库，作为条目的 `binary` 输出。
- 长时间任务（视频生成可能要数分钟到数十分钟）的处理：
  - **提交后，执行挂起**：节点状态为 `waiting`，执行释放槽位，`not_before` 设为下一次轮询时刻（复用 v2 §8.1）。这样长任务不会占满执行级槽。
  - 服务商任务 ID 写入意图记录（§18.8）。
- **提交的幂等性要说实话**：
  - 只有在服务商支持**幂等键或客户端引用 ID** 时，才能保证“接管后不重复提交”：提交时带上意图 ID 作为幂等键，接管时按幂等键查询。
  - 服务商不支持时，“已提交、但任务 ID 尚未写回”这段窗口内发生崩溃，**无法判定是否已提交**。此时节点标为 `unknown`，在执行详情中让用户选择“视为未提交并重试”或“放弃”，**不自动重提**，以免重复计费。
  - 每个服务商适配器都要声明自己支持哪种方式，并在节点面板中展示。
- 服务商异步节点**一律走意图机制**，不论是否标为纯节点。这里是对 §6.6.9“运行中的纯节点重新执行”的例外。
- 失败分类：额度不足、内容审核拒绝、参数错误、服务商故障。前两类不自动重试。

### 8.2 本地推理 worker `ferry-infer`（S4）

- **是什么**：自研的 Python 包，核心依赖 PyTorch（BSD-3）、diffusers / transformers / safetensors（Apache-2.0）。在 GPU 主机上以**常驻守护进程**运行，只监听 `127.0.0.1`，常驻是为了让模型在显存里保持热加载。
- **许可证要单独审查**：不是所有传递依赖都宽松。CUDA 相关 wheel 受 NVIDIA EULA 约束；常见 TTS 依赖 espeak-ng（GPL-3.0）；PyAV、decord 会捆绑 FFmpeg（LGPL/GPL）。依赖清单在 S4 逐个审查并记录。**平台不镜像、不再分发 wheel 和模型权重**，都由主机从上游下载。
- **安装与托管**：
  - **不能用 exec 通道启动守护进程**：`exec_stream` 结束时会杀掉整个进程组（`exec_stream.rs:38-58`，Windows 用 `taskkill /T /F`）。
  - 因此 Runner 需要**新增**一个守护进程托管能力，复用 Runner 现有的原生服务与监督代码（`crates/runner/src/service`），负责以下工作：
    - 创建虚拟环境并安装固定版本的依赖，依赖清单随 Ferry 版本发布并带哈希；
    - 启动守护进程，崩溃后自动拉起；
    - 健康检查。
  - 这是 Runner 的代码改动，**不涉及协议改动**：托管指令通过现有的 exec 调用 Runner 自带的子命令下发。
  
  Windows 和 Linux 的 NVIDIA 环境都支持，macOS 用 MPS（能力较弱）。CUDA 驱动由用户自行安装，平台只做检测和提示。
- **调用链**：服务端 → `HostChannel.exec_stream` 在 GPU 主机上运行 `ferry-infer client --request <file>` → 通过本机 socket 发给守护进程 → 流式返回进度、预览帧和结果。
  - **不需要新增协议帧**：沿用 exec_stream，与 v2 §18.1 一致。
  - **取消**：每个请求带请求 ID。客户端进程被取消时，先向守护进程发送取消 RPC，再退出，以免 GPU 任务在守护进程里继续运行；接管时也按请求 ID 查询并取消。
  - 进度和预览帧以 JSON 行输出，服务端解析后**只推送到执行事件流，不写入持久日志**，避免占用 v2 §21 的日志上限。
- **分段执行**：连续的 GPU 节点（以 `gpu:*` 内部类型相连）组成一个**分段**，整体作为一个请求发给同一个守护进程。分段内部的中间张量留在显存或内存中，不回传。这是 ComfyUI 单进程执行的等价物，也是 GPU 内部类型不能跨分段连接的原因。
- **显存管理**：守护进程维护模型的 LRU，显存不足时卸载最久未用的模型；分段开始前预估显存，不足时排队。

### 8.3 模型注册表与主机同步（S4）

- 表 `models`：`id`、`workspace_id`、`name`、`family`（如 sdxl、flux、wan-video、cosyvoice……）、`kind`（checkpoint/lora/vae/controlnet/upscaler/tts/llm）、`source_url`、`sha256`、`size`、`license_id`（SPDX 标识，或 `custom`）、`license_url`、`commercial_use`（allowed/restricted/forbidden，必填）、`restrictions`（文本）、`notes`。
- **许可证门禁**：`commercial_use` 不是 `allowed` 的模型，第一次使用时要求使用者确认许可条款，确认记录写入审计。模型权重的许可证与代码不同：例如有的模型仅限非商业使用，有的设有收入上限或使用限制。V6 选型**以许可证为第一条件**。
- 表 `host_models`：`host_id`、`model_id`、`state`（absent/downloading/ready/failed）、`path`、`verified_at`。
- **下载**：由主机执行：
  - 来源支持 URL、Hugging Face、ModelScope；
  - 下载过程校验 sha256，失败可以重试；
  - 需要令牌的模型源，令牌来自凭据；
  - 下载任务复用主机节点的执行机制，在执行列表中可见。
- **运行前校验**（对标 ComfyUI 的问题面板）：
  - 打开或保存工作流时，检查 GPU 节点引用的模型在目标主机组上是否就绪；
  - 问题面板列出“缺失模型”，每项提供“下载到主机”和“定位节点”。

### 8.4 GPU 资源

- **GPU 信息上报**：
  - Runner 的 Metrics 帧新增**可选**字段 `gpus: [{index, name, memory_total, memory_used, utilization}]`，加 `#[serde(default)]` 以兼容老 Runner；
  - 采集方式：`nvidia-smi --query-gpu`；Apple 芯片只上报名称。
  - 这是 v3 在协议上唯一的变更：在现有帧上加可选字段，不新增帧，不需要提升 `VERSION`（§13）。Runner 侧仍有代码改动（GPU 采集、守护进程托管）。
  - `nvidia-smi` 在每次采集时调用，Windows 下必须使用 `CREATE_NO_WINDOW`；采集失败时省略该字段，不影响心跳。
- **调度**：
  - 主机新增字段 `gpu_slots`：Runner 第一次上报 GPU 之前为 0；第一次上报后自动设为 GPU 数量，之后用户可以修改；
  - 一个分段占用一个 GPU 槽，锁名为 `gpu:{host}:{index}`，owner 规则同 v2 §8.2.2；
  - 节点设置可以指定 GPU 型号或最低显存，以此选择主机。

### 8.5 实时预览与自动试运行

- **采样预览**：本地推理时每 N 步推送一张低分辨率预览帧，编辑器节点上实时刷新，对标 ComfyUI 的实时预览。云端生成只有服务商提供的进度百分比。
- **自动试运行**（对标 ComfyUI 的“运行（更改时）”）：
  - 编辑器中可以开启自动试运行：参数一改，就自动以测试模式运行到**当前选中的节点**；
  - 只对纯节点和缓存友好的图有意义；
  - 有副作用节点的图不能开启，按钮置灰并说明原因。

- 应用页同样由共享表单组件渲染。

### 9.6 公开页面（表单、聊天、外部审阅）

- 公开页面是**单独打包的轻量前端**，复用共享表单组件的渲染器与配置格式（与 §9.5 一致）。不使用服务端模板渲染。
- **隔离**：
  - 推荐配置独立的公开域名 `FERRY_PUBLIC_ORIGIN`，与登录后的主界面不同源（V15）；
  - 未配置时退回同源，但公开路由使用严格 CSP（`script-src 'self'`，不允许内联脚本），不读取登录会话；
  - 用户撰写的 Markdown 一律经白名单净化，不允许原始 HTML。
- **地址**：
  - 表单触发和聊天使用**稳定的生产地址**，可以多次提交（与 n8n 一致），由服务端生成的随机路径段标识；
  - 外部审阅（人工节点）使用一次性 token，限时。
- **防滥用**：按地址和 IP 限频；可选验证码；每个表单设上传大小和数量上限，上传计入资产配额。
- 路由必须注册在前端 SPA 兜底路由之前（`assets.rs` 的兜底逻辑）。
- 是否允许不登录访问，由工作空间设置决定，默认关闭（V9）。

## 10. 典型需求的覆盖验证

下面每个场景都只用本文定义的节点搭建。“依赖”一列说明场景从哪一期开始可用。

### 10.1 开发编程

| 需求 | 搭建方式 | 依赖 |
|---|---|---|
| 推送 → 构建 → 测试 → 审批 → 部署 → 通知 | 流水线（v2） | v2 P1 |
| Issue 自动分诊并修复 | 工作流：代码平台事件（Issue 创建）→ LLM 分类 → If（可自动修复）→ 主机节点“运行 CLI 代理”（在开发主机上运行编程代理，输入 Issue 内容，产出补丁）→ Codeup / GitHub 节点创建 MR → 运行流水线（校验）→ 审批 → 合并 → 飞书通知 | S2 |
| 代码评审机器人 | MR 事件 → 读取 diff（集成节点）→ LLM 结构化输出评审意见 → 评论到 MR | S2 |
| 定时依赖升级 | 定时 → 主机命令（检查更新）→ 循环（每个依赖）→ 代理修改 → 流水线 | S2 |

结论：**完全覆盖**。v2 负责交付，工作流负责周边自动化与 AI 编程代理编排。

### 10.2 视频生成

```
表单触发（主题、风格、时长、比例）
 → LLM 结构化输出（分镜提示词列表 json<shots>）
 → 循环容器 for-each 并行（并发 3）
     → 文生图（关键帧，云端或本地）→ 挑选（人工从 4 张候选中选 1 张，可选“重做”）
     → 图生视频（云端或本地，异步轮询）
 → 主机节点 ffmpeg 拼接 + 背景音乐（音乐生成节点）+ 字幕
 → 资产库保存 → 通知（附预览链接）
```

用到的能力：

- 结构化输出、并行循环、媒体预览、人工挑选；
- 异步长任务与接管不重复提交（§8.1）；
- 纯节点缓存：改了某个镜头的提示词，只重算该镜头；
- 成本统计、GPU 调度（本地时）。

结论：**S3 起覆盖（云端）**，S4 起可以本地生成。

### 10.3 短剧制作

```
表单（梗概、集数、角色设定）
 → LLM：剧本（json<script>）→ 编辑（人工修改剧本）
 → LLM：角色卡 → 文生图（角色定妆照，固定种子以保证一致性）→ 挑选
 → LLM：分镜（json<shots>，每个镜头含角色、台词、景别）
 → 循环 for-each 并行（每个镜头）
     → 图像生成（参考角色定妆照，图生图 / 角色一致性能力）
     → 图生视频
     → TTS（台词，按角色选择音色）→ 口型同步（可选）
 → 循环 for-each 顺序（每集）→ ffmpeg 合成（镜头拼接 + 配音 + 配乐 + 字幕）
 → 挑选 / 审阅（逐集，可标记“重做第 N 个镜头”→ 从该镜头节点重跑，其余命中缓存）
 → 资产库 + 发布（集成节点，例如上传到对象存储或内容平台）
```

用到的能力：

- 多级结构化数据；
- 上百个镜头的并行。单次执行的节点执行数上限默认 5000，循环轮次另有上限；
- 人工编辑中间稿后只重算下游，这依赖“从此节点重跑”和缓存；
- 资产复用（角色定妆照作为资产在多集之间复用）。

结论：**S3 起覆盖**。角色一致性的效果取决于所选服务商或模型的能力，平台提供参考图输入与固定种子，**不承诺效果本身**。

### 10.4 长篇写作（小说）

```
表单（题材、篇幅、风格）
 → LLM：大纲（json<outline>）→ 编辑（人工修改大纲）
 → LLM：人物小传、世界观 → 数据表保存（作为设定库）
 → 循环 for-each 顺序（每章，携带状态 $carry = {前文摘要, 伏笔表}）
     → LLM 写作（输入：大纲本章节点 + $carry + 设定库检索（向量库））
     → LLM 评审（结构化：一致性、节奏评分）
     → while（评分 < 阈值且轮数 < 3）重写
     → 编辑（人工可选：每章或每 N 章审阅一次）
     → LLM 生成本章摘要 → 更新 $carry
 → 合并章节 → 导出 Markdown / DOCX / EPUB（主机节点或转换节点）→ 资产库
```

用到的能力：

- 顺序循环与携带状态；
- while 循环；
- 向量检索（保持设定一致）；
- 长文本的编辑节点；
- 逐章的成本与进度；
- 可以中途暂停，第二天继续：执行挂起时不占资源。

结论：**S2 起覆盖**（只需要文本能力）。

## 14. 安全

1. **代码沙箱**：
   - JS 沙箱没有文件、进程、原生模块，内存和时间有上限，网络受出站策略约束；
   - Python 只在主机上运行，由主机隔离；
   - 平台不对主机节点做沙箱承诺，界面上说明“主机节点以 Runner 的身份执行”。
2. **SSRF**：服务端出站请求默认拒绝私有地址段（§7.3）。
3. **公开页面**：token 有效期短、一次性，提交内容有大小限制，频率受限；外部审阅者只能看到该交互所需的数据。
4. **凭据**：只经由节点凭据槽使用，不进入条目、表达式、日志和缓存键内容。执行数据中出现凭据值时自动脱敏，沿用 v2 的脱敏规则。
5. **模型与内容**：
   - 模型注册时必须填写许可证；
   - 服务商的内容审核结果原样展示，平台**不做绕过**；
   - 生成内容的合规由使用者负责，界面明示。
6. **成本失控**：AI 节点有单次执行的成本上限（工作流设置），加工作空间预算（§5.6）；循环有轮次上限；并行有并发上限。
7. **多租户**：缓存、资产、向量库、数据表全部按工作空间隔离；缓存键包含工作空间。

## 17. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 范围巨大，长期并行可能导致质量下降 | 交付延迟、回归 | 严格按期验收；每期都有真实场景验收和全量回归；共用外壳先行，避免两条线各自造轮子 |

| 生成内容的合规风险 | 法律风险 | 服务商审核结果不绕过；模型许可证必填并展示；使用者负责的提示 |

### 18.7 循环、合并、条目溯源、重做、暂停、重跑的形式化规则

**条目溯源**

- `paired` 改为数组 `[{node, iteration_hash, index}]`：
  - Aggregate、Merge 的输出条目，指向多个来源；
  - Split 的输出条目，指向同一个来源。
- 表达式 `$('X').item` 的解析规则：
  - 沿溯源链向上找节点 X；
  - **刚好找到一个来源条目时返回它**；
  - 找到多个时报错：“无法确定节点 X 对应哪一条数据，请改用 `$('X').all()` 或 `.first()`”。这一行为与 n8n 一致。

**合并（Merge）触发条件与真值表**

触发条件：Merge 的**全部前驱都进入终态**后才求值，这保证结果与执行快慢无关。各输入的状态有：有条目、空（执行了但没有输出）、跳过（分支未命中或静音）、失败但继续。

| 模式 | 规则 |
|---|---|
| 追加 / 按位置 / 按字段（默认“任一输入有条目即执行”） | 有条目的输入参与合并；空与跳过视为没有条目；所有输入都没有条目时，Merge 记为 `skipped` |
| “等待全部输入” | 任一输入为“跳过”时，Merge 记为 `skipped`（不是失败）；任一输入为“空”时照常执行，用空列表参与；“失败但继续”的错误条目作为普通条目参与 |

另外两条规则：

- **始终输出**：节点只有在被执行时才生效。上游被跳过的节点不会因为“始终输出”而执行。
- **跳过的传播**：一个节点的所有输入都是“跳过”时，这个节点也是“跳过”；只要有一个输入有条目，就执行。

**循环容器**

| 项 | 规则 |
|---|---|
| 嵌套 | 允许嵌套，最多 3 层 |
| for-each 并行 | 并发上限默认 4。输出**按输入顺序**排列，与完成顺序无关。单轮失败的处理由容器的“轮次失败策略”决定：停止全部、继续（默认）、或在全部结束后再标记失败。 |
| for-each 顺序 | 可选**携带状态**：`$carry` 初值由容器参数给出，每轮结束时取子图中“携带输出”节点的输出 |
| while | 条件在**每轮结束后**求值，可以读取本轮输出和 `$carry`；最大轮数 ≤ 1000，默认 10 |
| 并发组合 | 容器的轮次并发、逐条节点的条目并发、执行级并发上限三者**取乘积后再受执行级上限约束**：同时运行的节点执行数 ≤ 执行级上限（默认 8，最大 64） |
| 只重跑失败轮次 | 执行详情提供“重跑失败轮次”：成功轮次复用，失败轮次重新执行 |

**重做（挑选节点的“全部不满意”）**

- 重做的标准写法是把“生成 → 挑选”放进 **while 容器**，条件为 `$json.redo == true`，并设最大轮数。编辑器在挑选节点的菜单中提供“包裹为重做循环”，一键生成这种结构。
- 重做轮次中，上游生成节点**自动绕过缓存**：重做轮次中，执行上下文的 `$execution.redo_round` 加 1，并作为缓存键的一部分。种子为“执行后随机”时，同时生成新种子。这样重做必然产生新结果。

**按轮次重跑**

- 重跑接口 `POST /workflow-executions/{id}/retries` 的请求体增加 `iteration`（轮次路径）。
- “从节点 X 的第 3 轮重跑”只重算该轮中 X 及其轮内下游，以及容器之后的下游；其它轮次复用。

**重跑的复用集**（移植 v2 §8.6）

- 设父执行的节点执行集合为 J，重跑闭包为 C。
- 闭包 C 按重跑方式确定：

| 重跑方式 | 闭包 C |
|---|---|
| 全部重跑 | C = J |
| 只重跑失败 | C = {非成功节点执行} ∪ 它们的全部下游 |
| 从节点 X 重跑 | C = {X} ∪ X 的下游；可以按轮次限定 |

- **人工节点的传播**：
  - 人工节点进入 C 后，默认**复用父执行的回应**，这一点与 v2 的审批不同：审批类人工节点要重新审批，并且它的下游也并入 C，规则同 v2；表单、挑选、编辑类沿用原回应。
  - 用户可以在重跑对话框中逐个选择“沿用回应”或“重新处理”。
- 复用集 R = J \ C 中的成功节点执行，标为 `reused`。
- 执行身份 = 重跑者（§18.6）。
- **执行数据被清理后不能重跑**：父执行的数据已按保存策略清理时，拒绝“从节点重跑”和“只重跑失败”，提示“该执行的中间数据已按保留策略清理，只能全部重跑”。

**暂停与继续**

- 新增接口 `POST /workflow-executions/{id}/pauses` 和 `/resumes`：
  - 暂停时，等运行中的节点完成，然后挂起执行，状态为 `waiting`，`end_reason` 记为 `paused`；
  - 继续时，从挂起点接着执行。
- “**以当前版本继续**”是一种重跑模式：例如写到第 30 章发现提示词需要修改，修改并保存后，以“从循环第 30 轮重跑 + 当前版本”继续。已完成的轮次复用，规则同复用集。

**执行数据保存策略与恢复的关系**

- 执行过程中**一律**持久化节点输出，接管、续接、挂起都依赖它。
- 进入终态后，再按 `save_data` 策略清理。
- 设为“不保存”的工作流，执行结束后不能从节点重跑；保存工作流设置时提示这一后果。

### 18.8 副作用意图的通用化

`pipeline_task_intents` 推广为 `execution_intents`：

| 列 | 说明 |
|---|---|
| `subject_kind`、`execution_id` | 流水线执行或工作流执行 |
| `node_key` | 流水线的 `job_key`，或工作流的 `node_id` |
| `iteration_hash`、`item_index`、`attempt` | 逐条处理的副作用节点（如给 100 个人发邮件），**每个条目一条意图** |
| `kind`、`state`（pending/started/done/unknown）、`external_id`、`idempotency_key` | |

- 唯一键：`(subject_kind, execution_id, node_key, iteration_hash, item_index, attempt)`。
- 子执行由 `execution_parents(intent_id 唯一, child_execution_id)` 承载，规则同 v2 的 `pipeline_run_parents`。接管时按意图找子执行，不会重复创建。
- 外部服务商的幂等规则见 §8.1；通知仍是“至多一次”。

### 18.9 节点纯度表与缓存键

**默认纯度**（节点设置中可以显式覆盖：副作用节点可以“允许缓存”，纯节点可以关闭缓存）

| 节点 | 默认 | 说明 |
|---|---|---|
| 控制、转换、数据解析、图像编辑、模板渲染 | 纯 | 输入相同，输出必然相同 |
| JS 代码 | **副作用** | 用户声明为纯以后，沙箱进入确定模式：`Math.random` 与 `Date.now` 使用由缓存键派生的固定值，`$http` 不可用 |
| HTTP 请求 | 副作用 | GET 也可能有副作用，或者返回随时间变化的数据 |
| LLM、Agent | 副作用 | 服务端不保证结果确定；用户可以显式允许缓存，适合调试阶段省钱 |
| 云端媒体生成 | 种子固定时为纯，否则为副作用 | 种子为“执行后随机”时，种子值在执行开始时确定，所以同一次执行内可以缓存（§18.4） |
| 本地推理 | 同云端 | |
| 主机命令、Python | 副作用 | |
| 人工、等待、触发、发送类（邮件、消息、写入外部系统） | 副作用，**不能**允许缓存 | |
| 容器、组件、子工作流 | 由内部推导：内部全部为纯时才为纯；子工作流一律视为副作用 | |

**缓存键**（缓存只保存成功的输出，错误条目与“失败但继续”的输出都不缓存）

```
sha256(
  节点类型 @ type_version @ impl_version            // 节点实现版本：实现修复后旧缓存失效
  + 服务商适配器版本（如有）
  + 规范化 params（表达式求值之后）
  + 输入条目（逐条节点：只用当前条目）+ 输入资产哈希
  + 模型标识：本地模型取 sha256；云端模型取“解析后的具体版本”，服务商只给别名时，该节点不可缓存
  + 凭据的非敏感配置哈希（base_url、区域、模型列表等，不包含密钥）+ 工作空间 ID
  + 重做轮次（§18.7）
)
```

- **粒度**：逐条节点**按条目缓存**。100 个条目中改了 1 个，只重算 1 个。
- 引用缓存命中的节点执行记录 `cache_hit_from`，画布显示 ⚡。

### 18.10 同步 Webhook 的规则

| 情形 | 规则 |
|---|---|
| 与并发策略的关系 | 同步执行**计入**工作流的并发组。并发组已满时：`queue` 策略回应 503（带 `Retry-After`），`queue_latest` / `cancel_in_progress` 不适用于同步模式，保存时拒绝这种组合 |
| 执行到等待或人工节点 | 先按回应模式回应：“立即回应”已经回应过了；“最后一个节点结束后回应”此时回应 202，并带上执行 ID；“由回应节点决定”而还没到回应节点时，同样回应 202 |
| 编排者被接管 | 回应丢失（连接已断开），执行由接管方继续。执行记录注明“同步回应未送达” |
| 超时 | 默认 30 秒，可设 1–300 秒，到时回应 504，执行继续 |

验收：并发组满时回应 503；遇到人工节点时回应 202；超时回应 504。三种情形都要有真实请求测试。

### 18.11 主机节点：凭据注入、输入安全与检出

- **凭据**：节点凭据槽中的凭据，以**环境变量**或 0600 权限的临时文件注入主机进程，不出现在命令行中。主机输出在回传时按凭据值脱敏，规则同 v2 §17.2。执行结束后删除临时文件。
- **输入安全**：
  - 主机命令节点的参数**不允许**把表达式直接拼进命令文本。上游数据只能以环境变量（`FERRY_INPUT_*`）或输入文件的形式传入，命令中按变量名引用。
  - 编辑器检测到命令文本中含有 `{{` 时，保存失败，并提示改用变量。
  - 这样可以防止来自公开表单或 Webhook 的数据造成命令注入。
- **不受信任输入 + 代理**：图中同时有公开触发（Webhook、表单、聊天、代码平台评论）和“运行 CLI 代理”节点时，保存时要求在代理节点之前放一个审批节点；如果不放，必须由发布者勾选“我了解提示注入风险”，这一勾选记入审计。
- **检出节点**：新增“检出代码”主机节点，复用 v2 的 `sources` 和代码连接（凭据走 T13 的安全注入方式），为编程类场景提供仓库工作目录。
- **主机端资产缓存**：缓存目录按工作空间分区：`<runner数据目录>/assets/<workspace_id>/<sha256>`。

### 18.12 JS 沙箱的进程模型（V13）

- **推荐**：服务端旁边运行一个**独立的低权限沙箱进程** `ferry-sandbox`，由服务端拉起。QuickJS 在这个进程中执行，具体约束：
  - Linux：使用独立用户、seccomp 和 rlimit；
  - Windows：使用 Job Object 和受限令牌；
  - macOS：使用 sandbox-exec 配置文件；
  - 进程内**没有** vault 主密钥，也没有数据库连接。
- 服务端与沙箱之间走本机管道。每次求值独立创建运行时，执行时间与内存上限由沙箱进程强制执行；超时则 kill 整个进程并重启。
- 桌面形态同样使用这个模型。
- 原因：QuickJS 历史上出现过内存安全漏洞。在服务端进程内执行租户代码，一旦逃逸，就能拿到 vault 密钥和全部租户数据。
- 表达式求值的调用量很大，同样经过沙箱进程，但走批量接口：一次请求求值整个节点所有条目的表达式。
- S1 的第一项工作是一个**技术验证**：
  - Windows（MSVC）与 Linux 构建；
  - 内存和时间上限确实生效；
  - 灾难性回溯的正则表达式会被中断；
  - 每秒 1 万次表达式求值的吞吐。

  验证不通过，就回到 V13 重新决策。

### 18.13 成本控制补充

- **预算预留**：AI 节点调用前，先按估算预留预算，调用后按实际结算。并行节点因此不会同时越过预算。
- **未配置单价**：工作空间开启预算后，凭据没有配置单价的 AI 节点直接拒绝执行，提示“请为该凭据配置单价，否则无法执行预算控制”。
- **工作流设置**新增 `max_cost`，作为单次执行的成本上限。
- **凭据级限流**：每个凭据可以设置 QPS 和并发上限，避免大量 429 错误。
- **Agent 迭代上限**：工具调用最多 20 轮，默认 10 轮。

### 18.14 执行数据的脱敏与静态加密

- `workflow_node_runs.output` 和执行日志在数据库中**加密存储**，复用 vault，AAD 绑定执行 ID。
- 脱敏**只在展示和导出时**进行，持久化的数据保持原样，因为续接和重跑需要原始输入。
- **固定数据**会进入定义和版本，因此把真实执行的输出固定下来时，编辑器扫描其中疑似密钥和个人信息的内容并提示。导出和模板化时，可以选择剥离固定数据。

### 18.15 限额汇总

| 项 | 默认 | 上限 |
|---|---|---|
| 单次执行的节点执行数（含轮次与重试） | 5000 | 50000（工作流设置） |
| 执行树（父执行与全部子执行）的节点执行数 | 20000 | 平台设置 |
| 子工作流调用深度 | 10 | 10 |
| 执行级并发 | 8 | 64 |
| 单个条目 / 单个节点输出 | 1 MiB / 16 MiB | 固定 |
| 循环嵌套 / while 轮数 | 3 / 10 | 3 / 1000 |
| 定义大小 / 节点数 | 2 MiB / 500 | 固定 |

子工作流调用的死锁规则：

- 父执行在等待子执行时，**不计入**并发组的饱和计数；
- 同一个工作流调用自己（递归），只允许在 `concurrency.scope = none` 时使用，否则保存时拒绝。

### 18.16 分期依赖的修正

- S1 中的“代码事件触发”“上游完成触发”依赖 v2 P1-1 的发件箱。S1 中审批节点的会签、自审规则，依赖 v2 P1-4。
- 修正后的顺序：

```
v2 P0 → S0 → { v2 P1-1、P1-4 的核心部分（通用表结构与规则）} → S1 → { v2 P1 其余部分 ∥ S2 } → …
```

- S0 只建立通用表的**结构**（`trigger_deliveries`、`human_tasks` 的列与索引），规则在 P1-1 和 P1-4 中实现。
- **规模校正**：S1 包含引擎、编辑器、沙箱、Webhook、表单、人工节点和主机节点，**明显大于 v2 P1**。§15 中“S1 的工作量与 v2 P1 相当”这句话作废。
