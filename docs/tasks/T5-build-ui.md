# T5 — 构建模块的界面

仓库、流水线、执行历史、执行详情与日志。

## 必读

- `src/components/dsl.ts` —— 配置契约。**资源页不手写表格**，这是 CLAUDE.md §12 写死的约定。
- `src/resources.tsx` —— 现有资源的配置写法，照着加。
- `src/components/ResourceTable.tsx` / `ResourceForm.tsx` —— 不要改它们的行为；表达不了的需求是扩展配置的理由，不是另开一份实现的理由。
- `src/components/HostTerminal.tsx` / `HostFiles.tsx` —— 非列表视图的既有写法（挂载时机、URL 同步、不可见时暂停）。
- `src/App.tsx` 里 `HostDetail` 的标签页做法。
- `docs/ferry-运维平台产品与技术方案.md` §17.4（接口）与 §17.5。
- `CLAUDE.md`。

## 1. 仓库与流水线：只加配置

在 `src/resources.tsx` 里加 `repositories` 和 `pipelines` 的 `ListConfig` 与 `FormConfig`。**不要为它们写新组件。**

- 仓库表单：名称、URL、默认分支、凭据（下拉，取本工作空间的凭据）、备注。
- 流水线表单：名称、仓库（下拉）、目标（`target_kind` 选主机或主机组，`target_ref` 随之联动成对应的下拉）、定义、备注。
- **定义字段**是 JSON，用等宽多行输入（`secret` 字段已经是 textarea，参考它的做法；如果 `dsl.ts` 里没有合适的类型，加一个 `code` 类型，而不是把 JSON 塞进普通 textarea）。保存失败时服务端会返回「第 2 步「构建」的超时时间必须…」这类完整句子，直接显示即可。

## 2. 执行历史

`pipeline-runs` 的 `ListConfig`：序号 `#number`、流水线、状态、触发人、耗时、开始时间。状态用徽标区分 `queued/running/succeeded/failed/cancelled`。

列表里不要做「触发」按钮——触发属于流水线，放在流水线列表的行操作里（`runItemAction(workspace, "pipelines", id, "run", {})`）。

## 3. 执行详情 —— 本任务唯一的新组件

路由走现有的 `view` 模式（`/{ws}/build/runs/{id}`）。内容：

- 概要：状态、流水线、目标主机、触发人、耗时、commit。
- 步骤列表：序号、名称、状态、退出码、耗时。**超时的步骤要和普通失败显示得不一样**——服务端已经区分了，界面不能把两者混成「失败」。
- 日志：按 `?after=seq` 增量拉取并追加，不要每次全量重拉。

日志轮询的要求：

- 运行中约每秒一次；**run 结束后停止轮询**，不要一直转。
- 页面不可见时暂停（`document.hidden`），恢复可见时立刻拉一次。参考 `ResourceTable` 里自动刷新的做法。
- 组件卸载时取消在途请求，不要在卸载后 setState。
- 日志可能很长（已验证 220 个分片），渲染要能承受；不需要虚拟滚动，但不要每次追加都重建整个列表。
- 新日志到达时，若用户已滚到底部则跟随到底；**若用户向上翻阅过，不要把他拽回底部**。

## 4. 取消按钮 —— 文案不许夸大

服务端的取消只停止服务端等待并标记 `cancelled`，**远端命令可能继续跑完**（§17.3 与代码注释都写了）。

按钮文案和确认提示必须如实，例如「停止等待并标记为已取消；目标主机上的命令可能继续执行完毕」。不要写成「终止执行」或任何暗示远端立刻停止的说法。

## 5. 权限

- 触发与取消要 `pipelines.run`，没有该权限时不渲染按钮（`ResourceTable` 的 `permission` 字段已经会过滤行操作，详情页里的按钮要自己判断）。
- 只读用户能看列表、详情和日志。

## 6. 导航

`src/nav.ts` 的构建组里加「执行历史」。注意 `nav.ts` 是菜单的唯一来源，不要在别处硬编码路由。

## 测试

- 纯函数必须有测试（`vitest`）：按 `seq` 合并增量日志（含乱序到达与重复 `seq` 不能重复渲染）、耗时格式化、状态到徽标的映射。
- 现有 11 项前端测试必须继续通过。

## 验收门槛

按**退出码**判断：

```sh
npm run typecheck
npm test
npm run build
cargo fmt --all -- --check && cargo check --workspace --all-targets && cargo test --workspace
```

服务端不该被本任务改动；如果你发现必须改，先说明理由。

**自己验证一次真实链路**：起服务、建仓库与流水线、触发一次、在界面上看到步骤推进与日志增长、结束后轮询停止。可以用 `scripts/test-pipelines.sh` 里的起法准备数据。把你实际观察到的写进报告（截图不必，描述清楚即可）。

**变异测试一次**：把日志轮询改成 run 结束后仍继续轮询，确认你的测试或检查会发现。如果没有任何东西发现，说明这条约束没有被测到，补一个。

## 不要做的事

- 不手写表格或表单，不改两个 DSL 组件的行为。
- 不改服务端行为。
- 不 `git commit` / `git push`。
