# 应用高可用拓扑与多部署驱动方案

状态：方案/实验阶段，不代表表内服务已实现产品兼容。用户补充范围：PXC、Redis Sentinel、NATS、Nginx、XXL-JOB、Ferry 多活；不得把所有 HA 等同于 Swarm 副本。

## 1. 分层与复用

项目依据：主方案“服务拓扑模板/可移植应用定义/目标驱动”三层边界；现有 v2 Application、Native/Docker/Compose/Stack 渲染、host-group 每目标计划和历史快照；Ferry 启动配置、NATS transport、SQL 租约/worker ID、文件存储。PXC 的专用协议与实验见《PXC三节点部署与恢复方案》。本文件扩充共同契约，不替换该实验。

| 层 | 责任 | 禁止混用 |
|---|---|---|
| 拓扑蓝图 | 服务角色、身份、依赖、复制/仲裁、初始成员、入口、恢复/升级步骤 | 不等同于容器 replicas |
| 寻址与发现 | 监听、成员互连、客户端入口、通告、发现方式和DNS/IP绑定 | 不把 0.0.0.0、容器临时IP、代理VIP直接当节点身份 |
| 存储 | 数据身份、卷/目录、故障域、备份、隔离和重建 | 本地卷重建不等于迁移原数据 |
| 部署驱动 | Native、Docker、Compose、Swarm 的渲染、执行、状态读取 | 不把原生主机部署假装具备Swarm调度 |
| 运维流程 | 首次初始化、扩缩容、故障恢复、更新回滚、审计/审批和单一执行所有者 | 不用一个“重启全部”覆盖所有服务 |

同一个应用蓝图按驱动生成目标计划。复用现有 `ferry/v2 Application` 作为每目标执行产物；跨主机角色编排、端点绑定和服务适配器目前没有产品模型，不擅自往v2加字段或宣称已注册。产品数据模型/API、迁移up/down在接入开发前补齐；本轮无产品数据库变更。

## 2. 服务目录：同一基座，不同协议适配器

以下数量是首批实验拓扑，不是所有生产环境的固定上限。外部协议仅指导适配器设计；实际产品字段以项目设计/实现验收为准。

| 蓝图 | 拓扑与身份 | 健康/入口/恢复契约 | 当前状态 |
|---|---|---|---|
| PXC | 三独立数据成员，多写复制；独立卷与故障域 | Primary/Synced/ready；唯一bootstrap；SST/IST；全停候选评估与隔离 | 8.0/8.4隔离故障实验通过；全停自动恢复未验证，未产品接入 |
| Redis Sentinel | 一个当前主、两个副本、三个Sentinel；主角色可变，成员身份稳定 | Sentinel仲裁/选主、客户端支持Sentinel发现；复制偏移/延迟；旧主归队必须成为副本 | 隔离协议实验通过，产品接入未完成；不能当Redis Cluster |
| Redis Cluster | 分片主节点及各自副本、槽位与集群总线 | 槽位完整、重定向、分片故障转移、扩缩容迁槽；客户端必须支持Cluster | 独立蓝图，不能复用Sentinel初始化脚本冒充兼容 |
| TiDB | SQL层TiDB、元数据/调度PD、持久化TiKV分别定义成员和故障域 | 分别验证SQL入口、PD仲裁、TiKV区域副本与调度；成员发现和客户端SQL入口分开；扩缩容须等待数据迁移 | 保留用户前述范围，未实现/未实测；不能用MySQL协议连通或NATS仲裁测试代替 |
| NATS Core | 多个活跃服务器，路由/客户端发现 | 路由完整、客户端重连、订阅恢复；不承诺持久消息恢复 | 和JetStream分开验收 |
| NATS JetStream | 多服务器，流/KV的复制与仲裁分别配置，独立store | leader切换、复制组、持久消息与consumer恢复；副本数不能超过可用节点 | 流复制/leader及持久consumer恢复实验通过，Ferry集成另验 |
| Nginx | 无状态多副本，一致配置；上游有独立健康条件 | 配置校验后原子reload；上游失败切换；两个Nginx不自动产生一个HA入口 | 上游失败切换隔离实验通过；VIP/LB/外部DNS另验 |
| XXL-JOB | 多admin共享数据库、调度协调；executor应用与实例分组 | admin登录/API可用不代表调度接管；验证同一触发不重复、故障后的调度和日志归属；executor自身幂等 | 新适配器待验证，不承诺Exactly Once |
| Ferry | 多服务实例、共享SQL/主密钥/命名空间、独立实例ID/目录、NATS和共享文件存储 | API/WS/Agent跨实例、执行租约/栅栏、worker ID不冲突、单实例退出恢复、依赖失败关闭 | 有代码与既有集群回归；整套依赖HA不因此自动完成 |

模板先使用现有应用模板/参数与凭据概念，不新增“数据库集群管理”等平行一级模块。类型差异由模板角色与能力展开；用户仍操作同一个应用的部署、监控、版本与恢复入口。

## 3. 寻址矩阵

| 驱动/目标 | 成员发现 | 客户端入口 | 编译前必须检查 |
|---|---|---|---|
| 单机Native | 已绑定且本机可解析的主机名/IP及实际端口 | 主机端口/已有入口 | 端口冲突、目录权限；不能仅靠三个进程声称跨主机HA |
| 多机Native | 每角色绑定SSH/Agent目标的私网IP或可解析DNS | 外部LB/VIP/DNS或协议客户端发现 | 跨机可达、明确故障域、每目标配置不同、host-group不是盲目复制相同成员身份 |
| 单机Docker/Compose | 同一用户网络的服务名；跨网络需显式可达地址 | 发布端口/代理 | Compose项目间DNS隔离；容器端口不等于主机映射端口；不能拿内部别名通告给外部客户端 |
| 跨机独立Docker | 私网DNS/IP和固定可达端口；没有内置跨机服务DNS | 外部入口或协议客户端发现 | NAT、端口、防火墙、TLS名称，不能拼接Compose服务名 |
| Swarm | 应用需要负载入口时使用服务VIP；需要成员身份/复制互连时用DNSRR/任务发现或稳定绑定 | published端口/代理/外部LB | VIP与成员地址语义、endpoint_mode、成员启动次序、任务IP变化、卷归属与容量 |

必须分别建模：

- 监听地址：进程在哪个接口接受连接；`0.0.0.0`只能用于监听。
- 成员地址：复制、路由、仲裁的peer端点；可由可验证的发现机制生成。
- 通告地址：服务返回给其他节点或客户端的地址；接收者必须能访问。Redis的data/replica/Sentinel通告分开，NATS的client/cluster路由分开。
- 客户端地址：业务使用的入口/发现清单；数据库多主不等于客户端只需轮询任意节点。
- 运行身份：与DNS/IP解耦；换IP不等于新成员，换卷/身份需进入替换流程。

IP和主机名均支持显式绑定；IPv6使用方括号端口格式并单独验证。自动检测仅提供建议值，用户确认后写入部署快照。地址无法证明可达或服务不支持当前NAT通告方式时，编译结果为“禁止”，不能静默回退localhost或临时容器IP。

地址绑定按服务能力判断，不能只做“DNS/IP”通用开关。Sentinel使用主机名时需核对当前Redis版本的 `resolve-hostnames` / `announce-hostnames` 与客户端支持；本轮实验只使用可达私网IP。NATS对外通告不能把内网容器地址直接返回给外网客户端。Nginx开源版本本轮验证的是请求失败后的被动摘除，不冒充已部署主动HTTP健康检查控制器。

## 4. 配置生成、漂移与生命周期

蓝图保存逻辑角色与引用；目标绑定保存每角色的主机/网络/目录/端口；适配器生成成员配置、环境、启动命令、就绪和恢复步骤。首领/主节点等动态角色由服务协议决定，不能永久写死“最初a就是主”。动态发现结果不能覆盖用户原始蓝图。

部署预览展示每目标配置差异、成员端点、卷身份、凭据引用、启动顺序、需要的仲裁和失败条件。保存、校验、预览、执行分别记录；配置渲染成功不代表目标能力或数据库健康通过。状态依据带时间戳的实时观测，保留未知/过期/部分失败。

生命周期按适配器定义：校验目标→预备目录/网络→首次初始化或加入→协议就绪→开放入口→监控；故障→摘流→确认故障域与隔离→重启/归队/替换→同步→接流量。全停恢复、主从切换、移除成员、删卷、重分片分别预览与授权，不能共享一个默认脚本。

同一操作只有一个持租约的执行者；SQL租约和远端执行栅栏复用现有执行系统。Swarm接管的任务由Swarm恢复，Native/独立Docker的服务级自动替换在适配器与fencing未完成前不提供；显示“人工恢复”，不能伪称自动调度。

## 5. Ferry自身多活的依赖契约

已有代码：`main.rs` 在配置NATS集群模式时要求共享数据库URL与共享主密钥；`cluster.rs` 使用Core NATS传递实时流、JetStream KV维护有时效的连接归属；worker ID和执行租约有现有SQL协调。`README` 要求各实例独立数据目录与实例身份，反向代理支持WebSocket，共享文件存储。

部署模板必须绑定：共享PostgreSQL/MySQL的可用入口、相同主密钥与命名空间、独立实例ID/目录、满足副本数的NATS JetStream、S3/经验证共享文件存储、支持WS的外部入口。不能把SQLite文件放网络盘当集群SQL；本机文件模式不能直接扩成多机共享。Redis当前配置/监控不是所有多活功能的必选依赖，也不能以“起了Redis”替代SQL/NATS协调。

验收拆开：Ferry实例失败、数据库主入口切换、NATS leader/路由失败、S3暂时不可用、Agent重连、活跃执行所有权接管、worker槽位回收、版本不一致升级。已有某一项PASS不能推出整套依赖HA已认证。现有`test-cluster.mjs`与Rust集群回归复用，另补完整依赖故障矩阵；旧CI只标历史证据，不冒充新方案端到端复验。

## 8. 各角色配置与恢复的具体区别

本节为后续适配器的执行契约，不是当前已经可提交的 Application 字段。配置键为相应服务的原生配置；蓝图到产品模型的映射在接入时评审。

| 蓝图 | 每个角色的配置差异 | 谁负责选主/恢复 | 必须拦截的操作 |
|---|---|---|---|
| PXC | 每成员独立 `wsrep_node_name/address`、目录和对等端点；唯一首次引导者，常态均配置加入地址 | Galera负责成员仲裁/复制；驱动负责进程存活；适配器负责安全加入与人工恢复计划 | 无隔离证明的重复bootstrap；丢卷成员以旧数据身份直接接流量；同步前加入可写入口 |
| Redis Sentinel | 数据成员持久目录与复制/通告地址各自绑定；Sentinel配置同一master逻辑名和可达端点，各自保存动态状态 | Sentinel仲裁选主和重配复制；驱动不能同时按初始配置强制旧主恢复主角色 | 每次重启覆盖Sentinel运行配置；将主节点固定DNS直接当永久写入口；以Sentinel切换承诺零丢失 |
| NATS JetStream | 每server独立server name/store目录，cluster name和routes一致；监听与client/cluster advertise分开；每stream/KV另设replicas | NATS选leader与追平；驱动重启实例；适配器验证复制组恢复 | 三server但stream replicas=1便宣称持久数据HA；复用同一store；无仲裁时强行删旧组重建 |
| Nginx | 多前端共享配置版本；各目标监听端点可不同；上游列表与健康策略来自被代理服务；外部入口另绑定 | Nginx负责请求级上游失败切换；驱动负责进程；外部LB/VIP负责前端故障切换 | 无 `nginx -t` 就reload；把失败后的写请求无条件重试并承诺无副作用；未提供入口仍显示端到端HA |
| XXL-JOB | 多admin共享同一数据库和兼容版本；executor设置应用组、实例地址、回调可达的通告地址与访问凭据 | XXL-JOB负责调度协调；executor业务负责幂等；驱动仅恢复进程 | 只用HTTP 200认证调度HA；重启admin即补发全部历史任务；以多admin承诺Exactly Once |
| Ferry | 各实例独立ID/目录、同一SQL/主密钥/namespace、NATS端点、共享文件与WebSocket入口 | 现有SQL租约/栅栏和NATS路由负责执行协调；部署驱动恢复服务进程 | 多机共享SQLite文件；同实例身份/目录；默认本机文件存储直接扩多机；绕过执行所有权接管任务 |

拓扑、协议角色和进程副本分别显示。例如“三台Redis + 三台Sentinel”与“Redis Cluster三主三从”是两个蓝图；“三个NATS server”与“一个stream三副本”是两层设置。失联、降级、不可写、同步中均不能折叠成同一个“运行中”。

网络分区须另验：Sentinel失去仲裁禁止再次选主，不表示旧主所在分区必然无法接受写入；客户端发现、旧主隔离和复制写入约束共同评估。PXC多写存在事务冲突，客户端重试必须有业务幂等策略。自动重启、协议故障转移、空卷重建、跨机迁移是四种不同操作，分别显示能力与证据。

驱动执行的差异也固定保留：Native生成每目标的程序/服务配置和目录，使用目标已支持的进程管理能力；Docker生成每主机的独立容器及固定可达端点；Compose仅在同一Docker主机生成项目网络与服务；跨机不把多个Compose项目拼成一个网络。Stack交给Swarm分配任务，成员身份/放置/卷约束仍由蓝图限定。任何驱动都不得因为缺少隔离、发现或存储能力，静默改为三份相同配置。

### 10.1 配置编译与预检

1. 服务适配器声明角色、成员身份、端点用途、协议探针、数据持久化与生命周期。驱动提供发现、进程管理、放置、网络和卷能力，两者分别校验。
2. 每个端点同时记录使用者范围：成员、同网络客户端、跨网络客户端或外部入口。以使用者所在目标发起解析与连通性预检；Ferry服务器能连接不替代目标主机能连接。
3. 配置预览列出每角色的目标、监听、互连、通告、业务入口和数据位置。成员名、端口、目录及通告缺失或冲突时阻断；不得静默套用相同成员配置。
4. 服务名可寻址不等于可以负载均衡；需要具体成员的复制、仲裁、executor回调必须解析到符合协议的成员。地址变化时按该服务的重新发现/重配置流程执行，不能只更新一份环境变量。
5. 已有运行集群与全新集群分开处理；发现已有数据、已有成员或身份冲突后禁止首次初始化。接管存量集群另立授权及验收，不由“部署”隐式执行。
6. 凭据复用现有空间凭据引用；配置和日志脱敏，预检与执行均复核空间/对象授权。正式持久化字段、API和DDL仍按第7节在产品接入前定义，本节不新增数据库模型。

### 10.2 自动化能力分级与验收

同一部署分别展示进程重启、协议故障转移、成员重建、跨主机迁移的能力与测试结果，不合并为“自动恢复”开关。服务已能在剩余成员继续运行，不代表已恢复原有冗余；没有备用容量、隔离证明或可恢复数据源时，成员替换保持阻断并展示原因。

### 11.4 本阶段范围与评审

本阶段执行HA实验与现有模板/市场机制核对，形成统一接入方案；未新增模板产品模型、迁移、页面或外部仓库。后续产品接入先明确索引版本、类型映射、来源/幂等字段、仓库连接预设字段、各三库DDL/up/down、权限和三语文案，再实施。上述模型“源未定义，待补”，不把方案字段当作已存在接口。

### 11.5 首批内容组织与初始化验收

一套目录同时容纳内置内容和Git同步内容。应用部署、构建流水线、节点工作流、仓库连接各自在既有入口选择模板，不新增四个市场一级菜单。独立Git仓库只在目录协议和安装闭环通过后拆出；先在本项目版本控制内维护，避免产品接口尚未稳定就维护两份内容。

| 内容组 | 模板职责 | 验收对象与绑定 |
|---|---|---|
| 单机Native | 程序产物、工作目录、环境、健康检查、升级/回滚 | 绑定产物和SSH/Agent主机；分别验证启动、异常退出、重启、升级失败回滚及持久目录保留 |
| 单机Docker | 镜像、端口、独立卷、健康检查与重启策略 | 绑定镜像和目标Docker主机；验证端口可达、卷保留、坏镜像/健康失败与回滚 |
| Compose多服务 | 应用与依赖的同机网络、服务名和独立持久卷 | 绑定单一Docker主机；验证依赖就绪、服务互访、重建及卷保留，不标多机HA |
| 服务HA | PXC、Redis Sentinel、NATS JetStream、Nginx、XXL-JOB、Ferry各自独立蓝图 | 每个蓝图按驱动、地址、存储和故障域分别验收；不因同服务另一组合通过就复用验证标记 |
| 关联构建 | 现有Go依赖构建；后续前后端/镜像关联构建 | 使用具体公开项目固定版本；检查产物在下游实际使用、校验与失败阻断，不只输出成功文字 |
| 节点流程 | 仓库报告；后续事件处理、文件转换与人工审批 | 输入、节点状态、日志、结果文件与失败分支都能查看；第三方凭据由选用者绑定 |
| 仓库连接预设 | GitHub、Codeup、纯Git各自支持的连接配置与显式事件订阅 | 预设不携带授权；选用者完成实际仓库/凭据绑定后提交，启用监控与通知仍遵守原资源权限和确认流程 |

空间创建只读取随产品固定的内置目录，不在事务内访问Git市场或第三方仓库。测试要求：无外网也能创建空间；两空间副本互不影响；删改后重启不恢复；模板无跨空间ID/密钥；缺绑定不能运行；非法模板导致事务回滚；存量空间不静默补齐。应用/流水线/连接各安装链路分别验证权限、失败反馈和回读，市场同步成功不等于目标资源创建成功。
